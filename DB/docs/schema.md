# OPC 数据结构说明

## 2026-10-26 客户确认后自主承接

`007_provider_claim` 增加独立客户／承接者 `negotiation` 会话与 `claim_proposals` 表，保存发布 ID、条款、JPY 报价、期限及客户实际确认身份与时间。提案条款和既有确认不可改写，更新须新增提案。新表具有统一维护字段、中文注释、并发版本和审计触发器。承接接口依据客户实际确认建立既有合作／负责人／条款／确认记录；需求锁和既有唯一约束防止重复归属。详见[流程与数据边界](../../Docs/development/provider-claim-workflow.md)。

## 2026-10-26 需求分类增量

`008_request_classifications` 新增 `development_platforms` 和 `development_types` 两张字典表，分别保存固定 `code`、中日 `name_zh/name_ja`、排序 `sort_order`、启用状态 `enabled` 及统一 `id/updated_usr/updated_at`。草稿 `request_drafts` 与不可变原文 `request_versions` 增加 `platform_code`／`development_type_code` 可空外键，每条需求可选择一个主要开发端及一个开发类型；NULL 表示未分类。原文版本上的组合索引用于本人需求分类检索，分类与历史原文版本同时保存。字典停用不删除历史关联；应用账号只读字典，不能自建新分类。下文基线表数量保留原阶段事实。

结构基线日期：2026-10-14；后端接入现状更新：2026-10-16。适用于本地 PostgreSQL 18 的 `opc_dev.opc`，结构实现以 [migrations](../migrations/) 为准。

## 1. 范围与约定

2026-10-14 建库阶段只建立持久化结构，当时未选择后端框架或实现 API。2026-10-16 已基于本结构采用 Python + FastAPI + psycopg 实施 [BackendService](../../BackendService/README.md)，提供真实 SQL 事务、HTTP API、单测与 Swagger／ReDoc。既有 `opc_dev` 的应用凭据尚未配置；独立 PostgreSQL 18 临时测试库验证记录见[后端验证](../../Docs/testing/backend-api-2026-10-16.md)。APPClient 和 FrontendAdmin 仍为 Mock，普通客户端不能直接连接数据库。

- 业务可读需求号与数据库记录标识分开。关系、范围、交付版本分别计数，不能混用。
- 所有持久化表统一具备 `id`、`updated_usr`、`updated_at`。原有复合业务主键保留，缺失 `id` 的表新增非空、单列唯一的 UUID；审计表保留原有自增整数标识。记录标识一经创建不可修改。
- `updated_usr` 关联账号，自动取当前事务 `opc.actor_id`，未指定业务账号的维护写入为 NULL；`updated_at` 自动记录新增/更新时刻。现有时间值保留，新补列的存量行按迁移时刻初始化；这些字段不代表原始业务事件发生时间。
- 全部表、视图及字段使用 PostgreSQL 中文对象注释；历史迁移不直接改写，由新迁移覆盖旧英文说明。后续新增字段和表遵循同一标准。
- 时间使用 `timestamptz`，数据库会话默认 UTC；业务界面按 `Asia/Tokyo` 显示。日元报价使用整数金额，报价不表示收付款。
- UI 偏好只有 `ja`、`zh`，默认 `ja`。需求、消息、文件名等原文使用 UTF-8，不按 UI 偏好改写。
- 文本状态使用 CHECK 约束，关联使用外键；没有用一个订单状态代表审核、发布、承接和履约全部状态。
- 不初始化演示账号、管理员、密码或业务案件。仅启用开发服务；不建立支付、钱包、托管、抽佣或正式认证流程。
- 普通更新使用 `row_version` 辅助后续 API 乐观并发控制；API 仍须在更新条件中携带期望版本。单有字段不会自动识别客户端的过期请求。

## 3. 版本与事务

需求先插入 `requests`，再插入 `request_versions`，同一事务完成。当前原文和范围指针使用延迟外键，在提交事务时校验。技术范围必须引用同一需求的确切原文版本；当前范围不能指向旧原文。`highest_activated_scope_version` 由触发器维护，清空指针也不能绕过激活版本防回退；未激活的新整理稿可以单独存在，不自动取代当前范围。

原始附件关联不能修改或删除，技术整理开始后不能再向该原文版本追加附件。后续补充使用新的原文版本；原文和附件集合应由后端在一次提交事务中落库。

一份范围的每类审核只记录一次决定，不能覆盖结论。修改范围或已审核参考资料时建立新范围版本并重新审核。这是本次实现的证据保存方式；审核分工、SLA 和完整状态转移仍待 API 契约确定。

发布必须同时引用当前范围的“合规通过”和“技术通过”，不能混用审核类型、别的需求或旧版本。`scope_files` 在第一项审核产生后冻结，`publication_files` 只能引用这份已送审集合。客户私有 `request_files` 不会自动进入发布资料。

新合作只可基于当前合法大厅记录建立。同一需求最多一份未关闭合作，同一合作最多一位有效主要负责人。确定负责人的入口与审批方式仍未固定。改派需要在事务中关闭旧关系并建立下一关系版本，记录原因。

合作中的条款引用具体已审核范围。交付须由当前活跃、仍获内部授权的负责人提交，并绑定双方已确认的条款版本；初次合作确认放在发布之后，不把“客户必须先确认才能发布大厅”定为规则。需求后来补充或大厅下架，不删除已确认合作的历史范围。

交付、质检、对客发布、客户验收分别记录。执行中或修改中才可提交交付，版本必须连续递增；内部质检通过才能发布最新版本；待客户验收时，客户才可对本人合作中最新、已质检且对客发布的交付作出决定。存在更新的内部未发布稿时，旧版也不能验收。完成合作必须已有最新版本的明确验收记录。没有自动超时验收。

数据库对发布/承接取得需求行锁，对交付/验收取得合作行锁，对参考集合/审核取得范围或交付行锁，配合部分唯一索引避免并发双写。后端应采用短事务、固定加锁顺序，并处理冲突重试；幂等表本身不会自动创建业务记录或返回缓存结果。

状态迁移不由触发器完整自动推进。后端在同一事务写入事实、更新状态、必要的 outbox 及归因信息。数据库目前保护核心证据关系，不能替代产品尚待确定的完整服务流程。

## 4. 文件和读取边界

`files` 存储原文件名、MIME、类型、长度、SHA-256 和私有对象键；不存大文件字节，也不使用公开 URL 或长期签名下载链接。附件、预览、名称和数量都应通过服务端同一权限判断。上传完成后不允许原地替换内容身份；替换文件建立新文件 ID。

`file_previews` 支持缩略图、分页图像、视频、表格及文本预览结果与处理中、失败、不支持状态。2026-10-14 建库时这些状态只提供持久化位置；2026-10-16 后端已实现本地私有原文件上传下载、可支持原图/视频/文本预览与人工安全检查证据。Office/PDF 转换、自动病毒扫描和生产存储仍未接入，不能把人工检查记录表述为自动扫描。正文或表格 JSON 可记录转换元数据，但大内容应使用私有存储。

两个视图提供大厅的发布过滤基线：

- `hall_requests`：当前版本、双审通过、未撤回、无有效合作的公开整理字段。
- `hall_reference_files`：在上述可见范围内已明确关联、上传完成且检查通过的参考资料元数据，不含存储键。

视图没有授予 `PUBLIC` 查询权限，也没有依据登录用户进行 RLS 隔离。当前后端在视图之上执行对象级授权，大厅默认 `internal`，对客户私有详情、合作历史、管理员、消息参与者和文件操作分别检查身份与关系；正式大厅受众仍需业务确认。不能将这些视图或全部 `opc` 表直接暴露给客户端。

代码仓库 URL/commit 的数据库校验仅检查固定标识形式，不证明客户能访问、归档存在、源码完整或测试真实执行。质检必须另存实际验证证据。当前没有执行任意代码的作业。

## 5. 审计与身份边界

关键表变更自动记录对象键与变化字段名，不把密码哈希、令牌、消息正文或私有文件内容复制到审计。当前可信后端在业务事务内设置 `opc.actor_id`、`opc.correlation_id`；这些值是归因元数据，不是认证机制。未设置时应用操作者为空，仍记录数据库连接身份。所有表的 `updated_usr` 采用同一事务归因，`updated_at` 由后置维护触发器自动写入；业务 SQL 应省略这两个字段，避免与一次关闭或答复的历史保护产生冲突。

历史版本、决定、消息和审计限制普通 UPDATE/DELETE；撤销授权、下架、结束负责人关系使用一次关闭。数据库所有者/超级用户仍能管理结构和绕过这些保护，不能宣称防篡改审计或完整合规归档。

2026-10-14 使用本机维护账号创建结构；2026-10-16 后端已实现密码哈希、会话用途隔离、对象权限和事务服务，并使用独立临时库的受限应用角色进行验证。既有 `opc_dev` 的专用应用角色与连接凭据尚需落实，生产部署和两端真实联调未完成。禁止用维护账号运行后端，或把 PostgreSQL 密码及连接信息打进 APP；访问方式见[后端 API 契约](../../Docs/development/backend-api.md)。

## 6. 后续演进

生产数据库部署、备份保留/恢复指标、生产文件容量、存储与转换供应商、外部通知投递、承接机制和资金规则尚未确定。后续变更新增编号迁移，不修改已应用文件；不通过删库重建处理真实数据升级。

PostgreSQL 参考：[约束与外键](https://www.postgresql.org/docs/18/ddl-constraints.html)、[CREATE DATABASE](https://www.postgresql.org/docs/18/sql-createdatabase.html)。跨行条件由外键、索引和触发器保护，没有用引用别行数据的 CHECK 伪装为稳定约束。
