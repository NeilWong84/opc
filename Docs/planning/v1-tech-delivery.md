# OPC V1 技术实施与开发交付方案

版本：当前边界评审稿 2.1。更新日期：2026-10-14。

**当前 V1 面向日本国内业务，只开发“AI 开发系统”服务。客户注册登录提交需求，后台进行合规审核与技术整理，审核通过后发布任务大厅；未通过的需求在大厅不可见。** 承接方暂为内部指定系统账号，指定账号不等于用户已确定逐单派单，也不等于已通过 OPC 认证。

长期五条服务线保留：Vibe Coding/AI 开发系统、数据与表格、文档、图文、短视频；后四条不属于本期 P0。未来正式承接方需考核并获得 OPC 认证，其流程另期建设。

旧跨境/开放承接方案及估算保存在[2026-10-08 历史版本](v1-tech-delivery-2026-10-08-history.md)，不再作为当前实施基线。范围见[统一方案](opc-v1-unified-implementation-plan.md)，接入准备见[三方方案](v1-third-party-services.md)。

## 1. 已明确与待决

| 项目 | 当前结论 |
| --- | --- |
| P0 业务 | 日本客户自助注册登录、提交原始需求、后台合规审核与技术整理、审核通过发布大厅、开发服务承接与交付 |
| 当前账号 | 内部指定/邀请的系统账号，有明确角色和启停；不开放公众服务者入驻 |
| 承接方式 | 大厅申请、直接接单或运营确认最终负责人未定；不能先将逐单手工派单写成唯一主流程 |
| 未来认证 | 考核与 OPC 认证另期规划；内部授权、身份验证、OPC 认证三者分开 |
| 已定两端 | 手机端：Flutter + Dart，覆盖客户与承接者的查看任务、注册登录、发布需求、接单、交付、反馈及验收；管理后台：Vue.js + TDesign Vue Next，负责审核、技术整理、发布、账号及运营管理 |
| 已定工程边界 | 仅手机端与管理后台，共用统一 `BackendService/` 后端；不新增独立客户 Web、承接者桌面入口或第三个平台端 |
| 本地数据库 | 已采用 PostgreSQL 18.4，2026-10-14 实际初始化 `opc_dev` 数据库与 `opc` schema；只写基础字典，尚未接入后端 API |
| 后端框架 | 未定；模块化单体仍为建议，按团队与事务/权限验证结果选择 |
| 部署与三方 | 未定；日本部署候选待验证；先评估合作内留言/通知，不默认采购 IM |
| AI | 可选渐进辅助，不能替代人工审核、自动发布、客户确认或承接权限 |
| 资金 | 签约收款主体、是否在线收费、付款时点、退款及内部报酬未定；旧撮合方案 A/B 不直接沿用，当前不默认钱包或提现 |
| 开发路线 | Figma Vibe Design → Vue/Flutter Mock → 测试环境真实 API → 预发布 → 生产 |

内部账号只是准入边界，不降低项目隔离、鉴权、撤权、审计或测试要求。历史五线功能、跨境互通和旧工期不能自动进入本期排期。

统一后端维护同一套业务领域、用户与角色授权、审核/发布状态、有效承接关系、文件版本和审计。手机 API 与管理 API 可以按权限、用途和响应字段划分，但不能复制成两套独立业务后端或分别保存互不一致的业务状态。后台发布的同一任务由手机端按权限读取，手机提交的需求与交付进入同一后端处理。

共用后端不等于共用管理员权限或令牌。手机普通用户会话不能调用管理接口；管理登录、MFA、会话范围和高权限操作单独控制，并由后端校验角色、令牌用途和对象授权。统一身份模型也不能使内部承接账号自动升级为管理员。本地数据库已选 PostgreSQL 18.4；后端框架、生产数据库部署和供应商仍未确定。

## 2. 最小模块与业务链

| 模块 | 本期职责 |
| --- | --- |
| 账户与角色 | 客户登录/恢复；内部邀请、授权、停用、会话撤销及管理端 MFA |
| 需求接收 | 接收自然语言和附件，允许“不确定/需协助”，保留原始版本，不要求客户懂技术 |
| 合规审核与技术整理 | 全部需求人工审核；指定整理负责人、提问澄清、形成范围、交付物、技术判断和验收建议 |
| 审核与发布 | 通过后才生成/发布对应版本的大厅任务；未通过、撤回或不具备发布条件的内容不能在大厅查询到 |
| 大厅 | 展示允许的任务摘要、状态与筛选；详情和附件分级授权，不公开客户全部原始资料 |
| 承接关系 | 根据待选机制建立主负责人关系，处理并发、退出、换人与权限，不提前锁定手工派单或直接抢单 |
| 开发交付 | 手机原生页面完成范围确认、进度、固定代码版本/私有源码文件提交、说明/测试资料、反馈修改、重提及验收；后台查看与运营处理仍受管理权限约束 |
| 沟通通知 | 客户可见留言、内部备注、未读及邮件；可先业务内实现 |
| 文件与审计 | 私有附件、隔离检查、版本与权限、访问审计、异常和备份恢复 |
| 可选 AI | 结构化、方案/说明草稿、验收清单建议；失败回到人工，不阻断主流程 |

审核/技术整理负责人是内部工作分工，与正式执行承接关系不同。可以由同一人员兼任，但权限和业务记录必须分开，不能因参与整理就自动取得执行或代客户验收权。

## 3. 数据对象与发布关口

建议对象：客户/联系人、内部账号状态、角色授权、需求原始版本、审核记录、澄清记录、技术整理任务、结构化范围版本、大厅任务及发布快照、承接申请（若选用）、有效承接关系及历史、合作确认、交付版本、验收反馈、客户留言、内部备注、文件、通知作业和审计。

2026-10-14 已按上述主要对象建立本地 PostgreSQL 基础表、约束与视图，实际结构以[数据库结构说明](../../DB/docs/schema.md)和迁移 SQL 为准。本次只初始化基础字典，没有导入演示账号、明文密码或业务样例，也未改动既有 `Accounts` 数据库。数据库的关系和版本约束不替代后端鉴权；尚未确定的承接获取方式、资金规则和正式认证不因建表而定案。初始化步骤见 [DB/README.md](../../DB/README.md)，执行及回滚验证见[数据库初始化记录](../testing/database-initialization-2026-10-14.md)。

审核、发布、承接、履约和文件检查是不同状态，不能混成“已通过”一个字段。例如审核可为待审核/待补充/通过/不通过；发布可为未发布/已发布/已下架；承接规则未定时不先固化申请/抢单状态机。

必须满足：

1. 客户原始表达不被内部整理覆盖；技术方案和范围有独立版本、编写人和时间，客户不必先知道框架、数据库或部署方式。
2. 每条需求均有授权人员的人工审核结果；AI 只能提出草稿，不可写“已人工审核”、直接发布或代客户确认。
3. 发布绑定已审核通过的需求/整理版本。审核后修改实质内容不能继续沿用旧审核结论直接公开，需按变更规则重新审核。
4. 大厅列表、详情、搜索、推荐、计数及相应导出、通知和缓存均受相同发布与权限条件约束；不能只在页面上隐藏未通过任务。客户本人的待审需求查询、审核补充通知及授权后台工作台按各自权限提供，不受大厅隐藏规则误伤。
5. 审核通过不等于客户全部原始附件公开。大厅摘要、可供内部承接账号查看内容与客户私有资料分别定义字段和访问权限。
6. 开发范围至少说明目标、包含/排除、交付物、验收办法、期限与修改边界；客户确认绑定准确版本。客户确认与大厅发布/承接各步骤的具体衔接在产品契约中冻结，不以“审核通过”伪装客户已经接受全部技术条款。
7. 交付/验收绑定版本；通知送达、AI 检查完成和文件上传均不等于验收。内部人员不能凭普通执行权限替客户确认。

范围或账号状态改变后，服务端需要复核当前条件，不能依据客户端旧状态或仅凭长期 token 中缓存的角色放行。

## 4. 承接机制尚未决定时的技术准备

| 待选机制 | 需要补充的规则 | 当前不能假定 |
| --- | --- | --- |
| 大厅申请 | 谁可申请、是否可撤回、谁选择申请人、通知与超时 | 提交申请即成为执行负责人 |
| 直接接单 | 资格、并发抢占、占用时长、退出/超时、是否需要客户或运营确认 | 所有内部账号都可抢全部任务 |
| 运营确认负责人 | 运营选择依据、权限、通知/接受、换人交接 | 这是当前用户已确定的唯一方式 |

在该决策前，可完成大厅浏览、人工审核和技术整理的原型/Mock，以及三种承接方案的简要交互比较；不要实现不可逆的唯一流程假设。真实承接 API、状态机和验收用例在机制冻结后落地。

无论选哪种机制，有效负责人关系都要版本化；例如 `assignment_version` 可表示承接关系版本，但不是“必须手工派单”的业务结论。内部整理分配使用独立关系与版本。若首版设一任务一个主负责人，该约束需由数据库与事务保护。

### 并发、换人与撤权的通用要求

- 建立/变更关系请求携带任务 ID、期望关系版本、作用的范围/任务版本和幂等键。服务端在事务内检查账号有效、内部承接授权、任务已发布且可承接、操作者权限、当前关系和版本；检查条件随最终机制补齐。
- 同一有效主关系不能因两次并发操作重复创建；版本冲突明确返回，不静默“后写覆盖”。同一幂等键重复提交不新增关系，相同键不同载荷应拒绝。
- 换人应关闭旧关系、建立新关系、更新权限、留存原因/历史并写通知 outbox；谁能发起/批准换人待规则确认。通知失败重试，不回滚已确认的主业务状态。
- 旧执行者后续读写、留言、下载和上传完成均核对最新授权。限时交接权限如需保留，应另设最小范围与期限，不默认永久保留。
- 上传初始化与完成确认、文件扫描/转换回调核对账号和关系版本；换人/取消后的旧作业不能自动成为有效交付。后台审计保留原作者，不能把旧交付改写为新人员作品。
- 停用账号后服务器拒绝新访问、撤销会话/刷新令牌，将未完成整理或执行任务列入待处理队列；不得静默自动选另一个人。
- 已签发直链可能在到期前继续有效。若需即时撤权，采用每次读取鉴权的代理/网关或可撤销令牌；否则明确有效窗口。已下载副本不能由服务器远程保证删除。

## 5. 账号授权与未来认证

服务端每次访问检查“账号有效 + 角色允许 + 该对象可见/被授权 + 当前状态允许”。大厅可见不代表可读全部原始资料；客户只能访问自己的需求与交付；普通内部账号不能越过项目授权查看他人工作资料。

内部账号状态可为待邀请/启用/停用，角色表达审核、技术整理、承接、运营或系统管理。未来认证应有独立认证记录、考核证据、认证版本/有效期和撤销状态，另期设计；当前不默认创建“已认证”记录或徽标，也不把内部邀请当作考核通过。

内部备注和客户留言使用不同可见类型并在服务器过滤；附件、通知和导出沿用同一权限。管理端处理审核、账号和运营工作；承接者的接单与交付在手机端完成。两端角色和数据授权均由统一后端执行，不靠菜单隐藏，也不把管理端凭证交给手机端。

## 6. AI 开发系统的文件与源码交付

最低源码交付为客户可靠可取用的固定版本：完整 commit + 客户有权限的仓库 + 归档约定，或完整 ZIP + 哈希；另附 README、依赖/许可、环境变量名称示例、测试说明、部署/回滚和验收资料。约定的演示链接只是补充，不能用可变 `main` 或演示站替代源码交接。

手机端必须原生支持填写仓库地址和完整 commit、选择及上传私有源码包/说明附件、查看上传与检查结果、提交交付版本、读取客户反馈、重提修改和确认验收。不能要求用户转到尚不存在的桌面平台才能完成交付；打开外部仓库或演示站只属于辅助查看。客户在手机端可查看当前交付版本、说明与反馈历史，并完成验收操作。

代码生产可在外部开发工具中完成，再通过手机提交固定版本或交付包，不新增第三个平台端，也不要求把 IDE 放进手机。源码包与附件需真机验证系统文件选择、较大文件上传、前后台中断后恢复、授权到期和版本冲突；手机界面必须正确反映后端的真实提交结果。

OPC 保存源码副本须获许可，不强制镜像所有仓库；不收长期 PAT、SSH 私钥、生产密码或云管理员凭证。预览站的账号、域名、运行资源、API 费用、到期和移交由合作约定，不继承 OPC 登录权限。

附件私有存储，上传检查类型、大小、完整性及恶意内容；压缩包限制路径、层级、文件总量和资源；适用时进行静态秘密扫描。没有权限取得源码时，由约定责任人提交检查结果，平台不能冒称独立复核。

不在平台宿主机执行客户代码、安装脚本、宏或未知工作流。自动沙箱、在线 IDE、自动部署另期评审。文件预览和扫描隔离执行并更新解析器，不能与主业务进程共用高权限。

本期仅为开发服务设计必要交付；后四条服务线的模板、转码、在线表格/文档编辑、图片/视频生成等不纳入 P0，实现模型可保留服务类型扩展点但不提前建设完整功能。

## 7. AI、日文和部署

基础流程人工可用后，按效果逐步加入需求结构化、方案与说明草稿、验收清单建议；需要时加入语言辅助。AI 输出需人工核实；不得替代合规审核/技术整理、自动发布大厅、直接决定承接人或保证代码通过验收。

调用记录任务、输入版本、允许资料、供应商/区域、模板版本、时间与费用；设置限额、超时、有限重试与人工降级。客户附件和源码不默认整包送入模型。当前模型供应商未选定，日本端点也需核查实际推理/日志位置。

客户关键界面、错误、确认、邮件与帮助以日文为 P0；内部语言按团队需要确定并使用资源化文案。中文资源支持不是中国业务重新进入首版。时间标准化存储，按日本时区展示；币种、语言、资料处理地域分开，记录 JPY 报价不等于已付款。

部署从一个明确主写区域出发，验证日本真实网络、私有存储、备份、日志和通知；不按历史跨境方案预建双区互通。本机数据库产品及版本已定为 PostgreSQL 18.4；后端框架、正式数据库部署区域、托管方式、运行账号与权限、容量和恢复策略仍以事务、权限、恢复、团队维护和成本验证为依据，不把本机初始化视为生产部署完成。

## 8. Figma 到生产路线与开发批次

路线保持 **Figma Vibe Design → Vue/Flutter Mock → 测试环境真实 API → 预发布 → 生产**。详见[Figma 到真实数据流程](v1-design-to-production-workflow.md)；业务范围以本轮统一方案为准。

| 批次 | 设计/Mock 与真实 API 的相同验收主线 |
| --- | --- |
| D0 规则与工程 | Flutter 手机端、Vue 管理端与统一后端契约；开发模板、手机客户注册、后台内部授权、日文资源、接单机制、Figma 与环境 |
| D1 需求到大厅 | 手机自然语言提交 → 后台待审/补充 → 人工合规审核及技术整理 → 通过/不通过 → 通过版本发布并在手机大厅可见 |
| D2 承接与开发交付 | 手机按冻结机制接单、确认范围、提交固定源码与说明、更新进度、处理修改及验收；统一后端保护有效关系与版本 |
| D3 真实依赖与异常 | 真实服务联调、并发与越权、停用接管、变更下架、文件和通知失败、日文与设备验证 |
| D4 运行与发布 | 日本网络、生产配置、恢复回滚、客服、监控与发布交接 |

每批先评审场景与 Figma 节点，再以统一数据访问层实现 Mock，最后接真实 API。Mock 覆盖未通过不可见、审核后改内容、发布失败、账号未授权、承接冲突、换人后旧提交、文件失效和通知失败。承接规则未定时，只做可替换的候选演示，不把其中一条当成已批准需求。

后端重新执行全部约束；页面不能成为审核、发布或权限的最终判断者。测试/预发布/生产的账号应用、密钥、桶、数据库、回调和发信目标隔离；生产禁用 Mock 开关，不在真实失败时返回模拟成功。

手机源码放 `APPClient/`，管理后台源码放 `FrontendAdmin/`，统一业务后端放 `BackendService/`。这三个已确定的源码项目承载两个前端和一个共享后端，不是三个产品端；不创建独立客户 Web、桌面交付端或其他源码项目目录。数据库迁移继续放 `DB/`。完成项同时交付代码、接口契约、迁移、测试和文档；不因内部账号少而省略一致性和越权测试。

## 9. 必须验证的行为

| 场景 | 通过条件 |
| --- | --- |
| 不懂技术的客户提交 | 不必填写框架/数据库，仍能提交并进入内部整理 |
| 人工审核关口 | 每条需求有审核人/结果/版本；AI 不能自动放行 |
| 未通过大厅访问 | 列表、详情、搜索、计数、推荐、导出和通知均不暴露未获发布授权内容 |
| 审核与发布版本 | 修改已审核的实质内容不会绕过重新审核；发布依据可追溯 |
| 原始附件保护 | 大厅摘要与客户原始私有资料权限分开 |
| 内部账号与认证 | 内部授权可启停，但不自动标识已获 OPC 认证 |
| 两端统一业务 | 后台审核发布的版本与手机大厅一致；手机提交、承接与交付均写同一业务记录，无两套独立状态 |
| 两端权限隔离 | 手机普通会话调用管理 API 被拒绝；后台高权限不因统一身份/后端自动授予承接账号 |
| 承接流程 | 按最终选择测试申请/接单/确认，不能靠历史手工派单假设验收 |
| 并发与幂等 | 不重复建立当前主关系；旧版本/重复请求得到明确结果 |
| 关系变化与停用 | 旧读取、留言、下载、上传完成和回调不能继续越权写入 |
| 客户与内部信息 | 内部备注、账号管理和报酬记录不进入客户 API、附件、邮件或导出 |
| 手机开发交付 | 手机上可提交固定 commit 或私有源码包、查看检查结果/反馈、重提及验收；文件选择、中断恢复、过期与冲突真机验证；平台不执行未知代码 |
| 失败与恢复 | 通知失败不篡改业务；恢复后审核/发布/关系版本一致，不恢复已撤授权 |

## 10. 排期、成本与待决记录
