# OPC V1 三方服务与开通准备

版本：当前边界评审稿 2.0。更新日期：2026-10-12。

**当前 V1 为日本国内业务，只开发“AI 开发系统”服务。客户注册登录提交需求，后台完成合规审核与技术整理，审核通过后才发布任务大厅。** 未通过的需求不能在大厅及其搜索、列表、推荐通知或关联接口中暴露；客户本人和授权审核人员仍可查看受理过程。承接方暂为内部指定系统账号；这是账号准入，不代表已决定逐单派单，也不等于已获得 OPC 认证。

长期保留 Vibe Coding/AI 开发系统、数据与表格、文档、图文、短视频五条服务线；后四条不属于本期 P0。未来正式承接方需经过考核并获得 OPC 认证，认证实施另期规划。供应商、后端、承接机制、经营主体和资金方案均未定。

旧跨境开放平台方案已原样保存为[2026-10-08 历史版本](v1-third-party-services-2026-10-08-history.md)。其中供应商能力、地区与价格仅为历史调研，未经本轮复核，不作为当前采购结论。技术实施见[技术方案](v1-tech-delivery.md)，当前产品口径见[统一方案](opc-v1-unified-implementation-plan.md)。

## 1. 开通原则与待决边界

- 先覆盖客户自助注册登录、原始需求、后台合规审核/技术整理、审核通过发布大厅、承接关系建立、开发交付及反馈。AI 不能代替人工审核或自动放行。
- 客户可以自然语言描述需求，不必懂技术或先选框架。原始需求与内部整理后的技术范围分别留档；运营代录只作可选辅助，不能替代客户自助入口或代替客户接受条款。
- 承接账号由内部授权人员指定/邀请并管理启停；不开放公众服务者注册。任务通过大厅申请、直接接单，还是经运营确认最终负责人，尚未决定，不提前锁定手工派单系统或自动抢单服务。
- 身份认证、内部授权、未来 OPC 考核认证分别记录；当前内部账号不得自动展示“OPC 已认证”。
- 已明确只有两个端：Flutter + Dart 手机端覆盖客户及承接者的注册登录、查看任务、发布需求、接单、交付、反馈与验收；Vue.js + TDesign Vue Next 后台负责管理。源码分别放在 `APPClient/`、`FrontendAdmin/`，共用 `BackendService/`；三个源码项目承载两个前端及一个后端，不新增客户 Web、承接者桌面端或其他源码项目目录。
- 身份角色、审核发布、有效承接关系、文件与审计由统一后端管理。管理 API 和手机 API 可以按权限区分，不复制业务后端；统一身份不等于管理员权限/令牌共享，供应商和后端框架仍待定。
- 日本部署区域是待验证建议；存储、备份、日志、邮件和 AI 的实际处理位置分别记录，不因日本业务就推定所有三方都在日本处理。
- 资金未定：重新明确签约收款主体、是否在线收费、付款时点、退款及内部报酬。旧开放撮合方案 A/B 不直接沿用；内部报酬不自动等于市场分账，当前不默认建设托管、余额和提现。

P0 表示首发流程必要能力，不等于必须购买某个 SaaS；P1/条件项只有在对应功能确定后启用。当前不采购数据/表格、文档、图文、短视频服务线专用生产平台。

电子签约、社交登录、企业 SSO、实时 IM、自动仓库同步、沙箱运行和自动预览部署均不是本期默认采购。代码生产可使用外部开发工具，再通过手机提交交付版本，不新增第三个平台端；平台不索取工具长期凭证。手机源码交付、反馈和验收不能依赖另一个桌面平台才能完成。

## 3. 发布、承接与权限的三方接入要求

需求审核结果、技术整理版本和发布状态由 OPC 服务端判定。第三方搜索、通知或缓存即使出现历史数据，也不能允许客户端绕过发布/访问检查。审核未通过、退回补充或撤回的需求不得提前推荐给大厅使用者；原始客户资料不因审核通过自动全量公开。

技术梳理负责人是内部工作分工，与执行承接关系不同。未来选择申请/直接接单/运营确认中的哪条路径，都必须在关系生效时检查账号有效、内部承接授权、任务可承接、当前版本及是否已被承接。可以保留 `assignment_version` 作为技术字段描述有效承接关系版本，其含义不预设“运营手工派单”。

承接机制确定后再冻结有关 API；如果一任务只允许一个主承接人，并发操作只能产生一个有效关系。换人、停用和取消需原子更新关系与授权，并校验旧上传/异步回调；不得因都是内部账号而放松项目隔离。

对象存储直链可能直到到期仍有效；若需换人后立即撤权，选择每次下载复核权限的代理/网关或可撤销令牌。仅缩短链接有效期不能宣称立即撤销；已下载副本无法靠服务器保证清除，需内部交接与删除约定。

通知使用最少摘要和不透明 ID，打开后重新鉴权。内部备注、候选承接人、内部报酬和人员记录不得混入客户接口/邮件。身份服务负责账号与会话，业务服务负责大厅可见性及项目授权，不互相替代。

## 4. 开通顺序

| 阶段 | 工作 | 交付物 / 主责 |
| --- | --- | --- |
| 0 规则 | 在已定手机端+管理端+统一后端下，确认承接机制、大厅可见对象与字段、登录方式、真实主体和资金边界 | 规则/角色矩阵及未决记录；产品 + 业务负责人 |
| 1 资产 | 域名、邮箱、云账号、MFA、预算；准备 APP 组织开发者账号、Bundle ID/包名、签名和渠道材料 | 账号台账与受控资料；运维 + 主体/发布负责人 |
| 2 基础验证 | 日本网络、选区、私有存储、邮件、数据库及备份；虚构资料测试 | 候选对比与验证记录；技术负责人 + 测试 |
| 3 核心接入 | 手机客户/承接身份、后台账号管理、人工审核技术整理、通过后手机大厅可见、手机交付反馈验收；统一后端联调 | 两端真实主链、越权、并发和撤权报告；后端 + Flutter + Vue + 测试 |
| 4 发布及按需增量 | 完成 APP 目标渠道和签名验证；具体推送方案、AI、支付按已批准范围执行 | 发布包、签名/渠道材料及增量配置、测试和预算；发布/模块负责人 |
| 5 日本试点 | 生产隔离、权限复核、监控、恢复、回滚和值班 | 小批客户与内部账号发布记录；发布负责人 + 运营 |

Figma/Mock 阶段不依赖全部三方采购完成；客户认证、服务端权限、存储和异步处理须在测试环境真实 API 阶段验证，不能直接把 Mock 切成生产数据。

## 5. 环境、验收与预算

区分 Mock、测试/预发布与生产；身份应用、密钥、桶、数据库、回调、邮件目标和预算隔离。测试邮件发白名单，生产禁止模拟成功开关。密钥值不进文档、源码或客户端；台账保存服务用途、主体、负责人、环境、处理区域、保留期、密钥引用、轮换、配额和成本。

必验场景：手机客户自然语言提交、后台审核与手机大厅版本一致、未审核/未通过任务不可见、AI 不能自动放行、手机普通令牌不能调用管理 API、原始私有附件不泄漏、内部授权不伪装认证、承接并发（机制确定后）、关系变化后旧权限/上传回调、停用账号、手机固定源码版本/私有文件上传及反馈验收、通知失败、APP 签名安装升级和备份恢复。

成本按“AI 开发系统”的手机端、管理端及统一后端范围重估：基础设施、邮件/身份、源码和附件容量、监控、人工审核技术整理、开发交付运营、APP 组织账号/构建/签名/渠道及真机验证；AI/支付按选择增量。不沿用旧跨境五线同时上线的容量和费用。客户或内部执行者使用的预览站、域名、运行资源、工具/API 费用归属进入合作约定，不默认由 OPC 承担。
