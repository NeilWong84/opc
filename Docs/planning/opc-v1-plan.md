# OPC 首版产品与实施规划

> 历史方案，已被 2026-10-12 的 [V1 统一方案 2.0](opc-v1-unified-implementation-plan.md)替代。当前为日本国内业务，仅开发服务；客户需求经后台合规审核和技术整理后发布大厅，内部指定账号接单，未来考核认证。下文中日跨境、五线同时上线、开放供给及旧估算不作为当前要求，原文保留供追溯。

版本：评审草案 0.1。日期：2026-10-08。本文提出首版范围与实施建议，作为后续 PRD、原型、技术选型和排期的共同输入；建议项尚不等同于项目负责人已确认的最终需求。

## 一 首版结论

建议首版建设面向中国与日本的 AI 技能服务平台，跑通 **需求展示与发布 → 匹配或应征 → 双语洽谈 → 合作范围确认 → 执行与阶段确认 → 版本化交付 → 验收与反馈**。其中，日本需求方是重要获客对象，主要由中国服务者承接，也支持日本服务者；国内市场同时保留。

**Vibe Coding 是重点服务，AI 数据处理、表格处理、文档处理、图文与短视频制作都进入首版服务目录。** 控制首版规模的方法是限定每类服务的任务复杂度、交付规格和运营容量，而不是把 Vibe Coding 或办公类 AI 服务后置。

首版优先验证真实需求能否形成合格交付和再次合作。AI 辅助应落实到需求梳理、跨语言沟通、方案或脚本草稿、执行指引及成果检查；创作者可以使用经过用途与授权检查的外部工具。平台无需在首版同时自研代码 IDE、视频编辑器和所有生产模型。

资金模式尚未由项目负责人确定。本文推荐先实施 **方案 A：撮合与合作交付记录，平台不代收项目款**，并保留 **方案 B：平台支付与结算** 的独立增量范围。两者必须在排期和对外承诺上区分。

## 三 服务范围与复杂度边界

业务目录建议配置为五条服务线，各自有需求模板、能力标签、报价方式和验收清单。首发不设可绕开范围的无约束“其他需求”直接成交入口；超出模板的需求先经人工澄清。

| 服务线 | 首版可承接的标准任务 | 必须交付什么 | 复杂度边界 |
| --- | --- | --- | --- |
| Vibe Coding，重点 | 展示网站、落地页、小型内部工具、原型、明确输入输出的脚本或自动化、既有小功能修改 | 源码版本、可运行说明、依赖与环境样例、验收用例和测试结果；需要时附演示环境及部署交接 | 先限制单个明确目标；不承诺首版可承接无边界大型系统、生产高权限代操作或高风险业务系统 |
| 数据与表格 | 数据格式转换、按规则清洗去重、拆分合并、基础汇总、报表与可视化 | 处理后文件、规则与变更摘要、异常清单，按约定提供脚本 | 以文件或脱敏样本为输入；首版不直接接管客户生产数据库 |
| 文档 | 排版、结构整理、模板制作、资料转文档、双语内容整理 | 可编辑文件及约定预览版、来源和待核实项、样式与目录检查 | 明确页数、来源、用途与语言；专业意见和事实真实性不能仅由 AI 保证 |
| 图文 | 商品场景图、说明图、尺寸适配、信息图与文案配套 | 指定尺寸数量的文件、可编辑文本或源文件约定、素材和工具使用说明 | 必须确认商品事实、允许变化项、素材用途；不以自动生成文字替代日文排版校对 |
| 短视频 | 固定规格产品展示、图生视频、素材混剪、字幕与配音处理 | 已确认脚本或镜头说明、成片、字幕及约定源文件、授权说明 | 首版限定时长、镜头和修改范围；复杂长篇漫剧、直播代运营另立后续模板 |

可以预置小套餐帮助理解，但套餐数量、报价与时长只是运营配置，不写死为平台统一承诺。软件、表格、文档和影音成果必须使用不同验收标准，不能全部用“上传附件＋点完成”替代。

## 四 产品端与核心模块

### 面向客户的入口

1. **Flutter APP：** 中国和日本用户均可注册、发现项目或服务、沟通、查看合作进度、提交或验收成果；支持需求方与服务者身份。
2. **响应式 Web：** 建议首版增加，重点服务日本需求方在电脑上上传资料、确认范围、预览代码演示或视频、集中反馈与验收；支持手机浏览器。同时提供服务者 P0 最小桌面入口，用于受控上传代码包／大文件、登记仓库及固定版本、提交交付说明和查看反馈；完整服务者桌面工作台列为 P1。
3. **运营后台：** 审核、匹配协助、服务模板、跨语言客服、合作异常、文件访问、业务指标与权限管理。P0 界面可先中文，但必须正确处理日文内容与双语客服模板。

新增客户 Web 是设计建议，尚未创建源码目录。建议后续采用独立的 FrontendPortal 目录，复用业务 API；不能把后台管理页面直接作为日本客户门户。

### 首版功能边界

| 模块 | 首版必须具备 | 首版可简化方式 |
| --- | --- | --- |
| 账户与角色 | 注册登录、市场与语言偏好、双角色、服务能力、账户管理与注销流程 | 国内手机号验证码，日本优先邮箱；第三方社交登录后置 |
| 需求与服务 | 五条服务线、结构化字段、草稿、审核、发布、暂停、案例与做同款 | 先使用经过运营确认的模板，避免通用拖拽表单系统 |
| 匹配与报价 | 类目、语言、能力、期限和容量过滤；应征、邀请、报价 | 规则筛选与人工推荐先行，AI 提供解释，不自动决定双方合作 |
| 沟通 | 文字、必要附件、原文与译文、通知、屏蔽与举报 | 不做实时音视频、多人社群或复杂协作白板 |
| 合作记录 | 同一版本的范围、金额币种、工期、修改次数、里程碑、验收标准与双方确认 | 一单一个主服务者；允许约定校对协作，但不做复杂团队分账 |
| 执行与交付 | 分类执行指引、阶段确认、成果版本、反馈、再次交付、验收 | Code 可按原型／功能／交接组织；视频可按脚本／成片；不做通用项目管理套件 |
| AI 辅助 | 结构化需求、中日翻译、方案／文案／脚本草稿、检查建议、额度和失败降级 | 成品生产由服务者选择合适工具；平台不要求首版托管所有生成或执行过程 |
| 信任与运营 | 能力样例检查、内容审核、授权记录、投诉申诉、客服、审计 | 邀请制供需与人工抽检；不以“实名”标签替代质量验证 |
| 国际化 | 中日文流程、模板、邮件、通知、时间币种、文件和合同版本 | 两种语言先做完整；英文仅保留扩展空间，不承诺首发覆盖 |

逐模块字段、优先级、状态与验收见[功能范围](v1-functional-scope.md)。

## 五 首版不承担的能力

首版建议暂不建设金币签到、广告赚钱、邀请返现、直播社区、金融钱包、复杂分账、多级分销、大型企业采购审批和多人团队项目。它们不直接验证当前核心接单与交付目标。

不承诺 AI 自动完成一切任务。平台的区别应当是帮助普通人在明确要求下完成有质量的交付；代码安全、业务正确性、日文表达、商品事实和版权条件仍需要相应的人来确认。

自动在平台运行客户任意代码、连接生产数据库、保管客户长期云密钥、代部署到客户生产环境，均不进入默认首版流程。Vibe Coding 可以通过安全交付源码、演示和明确的交接步骤完成，不因此被排除在首版。

## 六 中日业务路径与本地化

| 路径 | 首版应跑通的重点 |
| --- | --- |
| 日本需求方 → 中国服务者 | 日文需求、可追溯的中日翻译、允许跨境访问的文件、明确币种和时区、日文成果检查 |
| 日本需求方 → 日本服务者 | 日文流程和本地协作，不强制微信、中国手机号或中国身份证格式 |
| 中国需求方 → 中国服务者 | 中文流程、CNY 报价、国内客户端与通知可用 |
| 中国需求方 → 日本服务者 | 中文需求与中日协商、明确交付语言、经允许的跨境资料、合同币种和时区 |

四种组合均纳入 V1 设计支持，按实际经营、资料处理和服务能力条件启用；重点验证日本需求到中国供给，不默认所有区域和材料都可互通。服务者选择以能力、工作所在地、可承接范围和交付语言为依据，不把国籍作为质量评分。

界面语言、用户所在地、服务市场、合同主体、交付语言、数据区域和币种分别建模。日元与人民币不能都只显示“¥”；截止时间明确展示日期及时区。正式条款保存原文和经确认译文的同一版本，不能在双方确认后随意刷新翻译。

日本交付检查不只检查文案：软件要检查日文界面与错误提示；数据与表格要检查编码、日期、金额、舍入与公式；文档要检查日文字体和分页；视频要检查字幕、读音和产品事实。具体设计与现行官方资料见[国际化及本地化方案](v1-cn-jp-localization.md)。

## 七 资金与经营方案

### 方案 A 推荐的首轮试点方案

OPC 提供信息、匹配、沟通与合作交付记录；需求方和服务者明确各自签约及付款安排。平台保存协作范围及用户声明的外部付款状态时，应清楚标为当事人声明，不能显示“平台已担保到账”。验收完成与收款完成分别记录。

方案 A 不等于“所有行为均无责任”或“无任何经营手续”；角色、平台协议、跨境资料、投诉和应用发布仍需要按实际业务落实。也不能把微信或支付宝个人转账列成所有跨境合作的统一解决方案。

试点是否收费建议先看获客和交付成本。可以先对邀请用户免费验证，不在未定义权益、开票主体和商店规则前上线会员、抽佣或充值。此为试点建议，尚非用户确认。

### 方案 B 如果首版必须平台收款

必须追加支付订单、支付结果回调、幂等、退款与部分退款、对账、收款主体、服务者入驻核验、结算周期、费用承担、跨境付款、争议或拒付、税务凭证等产品和后台范围。软件项目分阶段验收与分阶段付款是不同能力，不应自动绑定。

日本收款账户可用不代表可以向中国服务者自动打款。Stripe 当前文档的自助跨境打款覆盖范围并不直接涵盖本项目需要的日本平台到中国服务者路径，需按实际主体和支付机构确认可执行方案。[Stripe Connect 跨境打款说明](https://docs.stripe.com/connect/cross-border-payouts)

**本轮不替用户确定收付款模式。** 方案 A 可作为工程估算基线；若选择 B，需要先验证完整资金路径并重估范围，不能只增加一个支付按钮。

## 十 运营与度量

建议冷启动由现有日本需求方提供样本，中日服务者完成能力样例，运营协助首次匹配。Vibe Coding 设置代码交付评审责任人；办公服务设置数据核对责任；日文业务设置语言检查和客服责任，角色可以兼任但责任要明确。

首版重点统计有效需求获得合格应征的时间、合作确认率、按时交付率、首次验收率、修改轮次、投诉原因、再次合作率、每单人工与 AI 成本。代码交付额外看可复现运行和验收用例通过情况，数据类看对账与异常率。各市场、服务线和跨境路径分别统计。

方案 A 中报价总额只能称已确认合作报价金额，不能称平台实收 GMV。统计分母、归属日期、去重规则和取消单处理在 PRD 中固定。试点阈值依据样本与运营容量制定，当前不编造已验证的转化率或市场份额。

## 十一 后续需求与工程工作

阅读顺序建议：本文 → [功能范围](v1-functional-scope.md) → [国际化及本地化](v1-cn-jp-localization.md) → [三方服务](v1-third-party-services.md) → [技术选型与开发流程](v1-tech-delivery.md)。

3. 做中日网络、IM、文件、翻译、代码交付和发布条件的验证，再决定后端与云拓扑。
4. 按纵向业务场景开发，优先跑通日文需求到中国服务者交付，再覆盖所有服务模板与客户端。
5. 以业务验收、区域网络、权限、成本、运维恢复和发布材料共同决定首发范围。
