# OPC V1 日本单市场本地化与内部协作方案

版本：当前范围下的设计草案 v0.4。更新日期：2026-10-12（Asia/Shanghai）。

本文根据项目负责人最新范围编写，配合[OPC V1 统一落地整体方案](opc-v1-unified-implementation-plan.md)用于需求、原型、权限、接口和验收设计。它不代表已经实现、已采购或具备正式上线条件。[原中日方案](v1-cn-jp-localization.md)已标记为历史，不再提供当前 V1 范围。

当前无需建设公开服务者注册、开放供给市场、跨境匹配、中日自动翻译或跨境收付。其余四条服务线不开放发布或接单入口，不经“其他”分类绕过当前只开放开发的边界；是否展示预告由主方案决定。基础文案资源化和标准字段仍有价值，但不因此扩大当前版本的语言、国家和供应商范围。

“内部成员”描述业务准入与账号范围，不自动代表劳动雇佣关系或某种法人关系；日本国内承接也不按国籍判断成员资格。

## 2. 简中/日语界面与日本本地格式

- 客户在手机端自行注册登录提交开发需求，主流程默认日文并提供完整简体中文：注册/登录/找回、开发服务与案例、任务查看、需求提交、待审/补充/驳回反馈、范围与报价确认、沟通、进度、交付、修改、验收、客服和账号处理。内部承接者使用同样两种界面语言。具体身份验证方式另行确认，邮箱可作为日本侧首选建议，不默认增加社交登录。
- 客户入口以自然语言、期望效果、参考样例和附件为主，不要求不懂技术的客户先填写框架、数据库、接口、部署或模型参数。客户已知的用途、交期、预算和约束可以表达；未知项允许内部人员澄清。
- 界面语言包覆盖表单校验、错误、空状态、权限提示和附件说明；邮件、推送及正式条款在真实能力接入时按已确认的交付语言准备，不能将界面切换当作自动翻译。日本客户所需的对外文案、关键服务说明和正式条款由具备相应日文能力的人员检查。
- 姓名和公司名支持汉字、假名、拉丁字符与合理空格；不套用中国手机号或身份证规则。手机号、读音、地址、税务信息只在业务需要时收集，不因本地化而全部设为注册必填。
- 手机与后台管理界面均使用资源化文案支持简体中文、日语切换，术语统一，覆盖导航、表单、按钮、状态、错误、空状态和弹窗；不增加其他语种。日期金额采用格式化组件，但语言选择不改变 JPY 币种或 JST 时间语义。
- 手机登录页与个人页提供「日本語 / 简体中文」入口。语言选择通过 SharedPreferences 保存，重启恢复；退出登录和重置演示业务数据不清除选择，只保存 locale，不保存账号凭证或业务资料。快速切换须保持最后选择，保存失败应可反馈和重试。
- 明确服务用语，例如报价、交期、修改次数、交付格式、验收和售后。具体日文表达通过客户理解测试与人工审校确定。
- 中文/日文输入法组合输入、全半角、长公司名、标点、换行和大字号需要分别验证。界面图中文字与案例说明同样纳入检查。

APPClient 的语言源文件位于 `lib/l10n/parts/*_{ja,zh}.json`。在 APPClient 目录执行 `python tool/merge_l10n.py` 生成 ARB，再执行 `flutter gen-l10n` 生成 Flutter 本地化代码；两种语言须具有一致的键及占位符。新增文案维护源资源，不手改生成的 Dart 代码，不把客户原文写进语言包。

手机端同时提供承接者的大厅、接单、沟通、交付和修改入口。固定源码版本、文件与测试说明可以从手机提交，客户从手机查看材料并完成反馈验收；不要求额外 OPC 桌面门户。代码制作及特定运行用例可在对应外部开发环境完成，验证证据与结果回到同一交付记录。管理端使用同一后端的审核、发布和交付数据，按后台角色授权处理。

建议每份报价固定 JPY，明确税费是否包含及其他费用，不实现首版参考汇率或多币种结算。金额精度按币种处理，不采用浮点数计算；日元金额不默认添加两位小数。税率、票据类型与开具方根据实际主体及交易确定，不在前端硬编码未经确认的经营规则。

建议事件时间保存 UTC，交期同时记录 `Asia/Tokyo` 与双方确认的本地日期时间，对外注明日本时间。自然日和工作日分别表达；涉及工作日时保存所用日历与版本，并明确公司休业日。修改设备语言或时区不应改变已确认交期。

手机与后台的语言切换只改变界面文案，不自动翻译或覆盖客户原文、附件名、沟通内容、交付说明，不改变需求及审核版本、时区、金额、已确认交期或权限。界面语言、交付语言、用户所在地、合同主体、存储/处理区域仍是不同属性；增加中文界面不增加中国业务市场。使用日文或 JPY 不证明业务资料只在日本处理。

## 3. 内部指定账号与项目权限

内部成员准入不依赖公众注册或公开服务者申请。建议由授权管理员创建/邀请个人账号、分配角色并停用；避免多人共用一个承接账号，确保接单、提交和修改可追溯。客户注册成功不自动取得承接权限。采用何种身份系统、是否统一企业登录、管理员多因素认证等在技术选型时明确。

当前账号记录“内部授权/可承接状态”，不展示“正式 OPC 认证”标识。未来的考核及认证状态与当前内部授权分开设计：拥有指定账号不代表已通过未来考核，具体认证规则与申请流程后续确定，不纳入当前开发服务上线门槛。

| 角色 | 建议可见范围与动作 | 边界 |
| --- | --- | --- |
| 客户 | 自己有权访问的需求、报价、项目进度、交付和客服记录 | 不能查看内部备注、成员权限或其他客户资料 |
| 内部需求审核人员 | 对每项提交做合规审核、需求方式与技术整理、提出澄清、形成技术范围及日文验收方案，并记录审核结论 | AI 只能辅助；未经人工审核通过不能向任务大厅发布，内部草稿不能冒充客户已确认要求 |
| 内部承接成员 | 使用受控账号查看权限范围内已审核发布的开发任务，按最终确定的机制接单；获取获授权项目及必要附件，执行、沟通和提交成果 | 不默认读取待审需求、未脱敏原附件或所有客户项目；内部授权不等于 OPC 认证 |
| 项目负责人/协调人 | 在授权范围中跟踪承接、范围、交期与处理异常 | 具体分配机制待定；如发生人员调整，记录操作者、原因及权限变化 |
| 内部质检人员 | 授权检查对象、对应版本、验收标准和反馈 | 不因质检身份而自动获得全部生产系统或全部客户文件权限 |
| 账号/系统管理员 | 创建、停用账号与配置角色；业务资料访问另按职责授权 | 系统管理员不默认具备任意读取客户素材的权利 |

当前固定发布顺序为：**客户注册登录并提交自然语言/样例/附件 → 后台人工合规审核与需求方式、技术整理（必要时退回补充）→ 审核通过 → 发布到任务大厅 → 指定内部账号按受控机制接单**。指定账号定义“谁有资格接单”，不定义“每项任务必须由管理员指派给谁”。具体领取、申请承接或分配规则留待主方案确认。

任务大厅只返回审核通过且已发布的需求版本；待审、补充中、驳回和未通过版本不可通过列表、搜索或详情接口绕过审核。需求所属客户可在自己的需求记录中查看其审核状态，审核人员按权限查看待审资料。大厅可见信息与原始私密附件分开，审核通过不等于全部附件可向所有内部成员公开。

正式执行前仍需向客户用日文确认对应版本的范围、交付物、报价/交期与验收方案；客户确认与“审核后发布到大厅”是不同动作，审核通过不能代替客户的合作承诺。不得把客户确认前禁止正式执行写成当前必须逐单派单的依据。

所有需求均经过该人工审核路径，不能因为使用标准模板、命中 AI 分类或是老客户就自动免审。发布后的重要变更形成新版本并重新审核，未通过的新版本不能替换大厅已审核内容；影响已确认合作范围时还需客户重新确认。对客户展示可理解的成果、限制、费用/交期和验收方式；技术选型及实施字段由内部整理，不向客户转嫁填报责任。

账号停用、成员离岗或项目转派时，撤销会话与后续文件访问权限，保留必要审计和历史提交署名；不能承诺收回已下载的本地副本。若内部沟通与客户沟通共用系统，内部备注和草稿不得默认同步给客户。

## 4. 当前开发服务与后续服务线的日文交付要求

下表保留长期五条服务线的检查方向，**只有“开发（AI 开发系统）”属于当前 P0，其余四条为后续参考，不要求当前建设或完成验收样例。** 技术字段是内部审核、整理与交付检查清单，不是要求客户自行填满的发布表单。内部人员将自然语言需求整理成专业要求，再以客户看得懂的日文成果说明、示例和验收步骤确认；正式执行前确认范围和验收方案，不强制预设每单由管理员指派。

| 服务线及阶段 | 日文本地化与交付要求 | 验收证据 |
| --- | --- | --- |
| 开发（AI 开发系统）— 当前唯一开放 | 明确目标用户、软件界面语言、设备/浏览器、功能范围、运行环境及支持期限；源码、依赖/许可、配置示例和部署说明与固定版本关联 | 客户可取用源码并按约定复现关键用例；日文输入、错误、长文本、JPY、日期时间检查记录；不以 AI 生成或演示链接代替验收 |
| AI 数据与表格 — 后续 | 明确字段、清洗/计算规则、编码、日期格式、金额含义、公式及异常处理；优先用最小合成/脱敏样本表达问题 | 行数、汇总和差异可核对；前导零、长编号、精度、日文字符、CSV 编码及公式未被静默破坏 |
| AI 文档 — 后续 | 明确读者、用途、日文术语、客户模板、可编辑格式及预览稿；检查事实、数字和引用 | 日文自然度、字体、分页、段落、表格、目录和链接检查；可编辑稿与预览一致 |
| AIGC 图文 — 后续 | 明确尺寸、数量、渠道、品牌名、图中文字、产品事实和素材许可 | 成品规格、日文排版、金额/商品信息正确；许可和约定的 AI 标识记录可查 |
| 短视频 — 后续 | 明确脚本、时长、画幅、字幕、声音语言、配音及音乐许可 | 脚本版本、日文读音与字幕、声音画面质量、渠道规格及许可检查记录 |

每次范围、报价、阶段确认和验收关联同一版本。内部草稿由责任人确认后再发送客户；AI 可以辅助需求整理、方案和检查，不自动形成正式报价、不自动宣告代码测试通过或替客户验收。

中日自动翻译不作为当前必需能力。如实际内部团队需要翻译，再明确所翻译内容、供应商、处理区域和原文/译文版本；关键条款仍由人员确认。原文及必要历史按对应保存期限保留，不使用无期限留存作为默认。

源码交付检查第三方依赖和许可；资料上传、聊天与模型输入不接收生产密码、私钥、长期令牌或真实数据库连接凭证。内部成员使用客户生产环境也需要单独授权、最小权限及撤销安排。平台不因内部分工而默认执行上传的未知代码、SQL 或宏。

客户素材仅用于约定服务。公开案例需要单独授权；人物、声音、字体、音乐与其他第三方素材按实际用途检查许可。“已内部验收”不自动扩大作品的权利范围。

## 5. 日本国内业务的数据处理条件

日本需求与日本承接描述供需关系，不能证明云、模型、IM、客服、日志或备份没有境外处理。此次不新增法律适用结论，也不预先断言必须日本单区或可任意跨区。

| 数据环节 | 选型前必须确认 | 建议控制 |
| --- | --- | --- |
| 客户到平台/内部成员 | 收集内容、用途、成员角色、需要访问的项目和保存期限 | 项目级权限、最少必要资料、私有附件、访问记录 |
| 平台到 AI/翻译/检查服务 | 实际处理区域、留存、训练用途、子处理者及客户允许范围 | 服务端统一调用、工具/区域限制、最小输入、费用限额；禁止静默跨国兜底 |
| 文件、IM、邮件与推送 | 文件/正文保存位置、接收者、链接权限及保留期 | 文件按项目授权；通知尽量不含私密正文；内外消息分离 |
| 日志、备份与支持访问 | 内容是否包含个人信息/素材、复制区域、供应商支持与管理员访问 | 日志脱敏、按角色访问、保留期限、恢复和删除验证 |

云与 AI 地区确定后，维护简明数据流清单，记录数据类别、接收者、目的、区域、保留、再委托和删除方式。若发现实际境外提供或处理，针对该条资料路径核对合同、告知和其他适用条件；这不等于恢复跨境供需市场或新增跨境支付需求。

含个人信息、客户数据库或商业秘密的文件不能因为“内部承接”而自动整份送入 LLM。可采用脱敏样本、客户环境处理或只交付处理脚本；去掉姓名也不必然消除关联识别风险。

删除账号、业务留存、争议证据和供应商副本分别管理，告知实际范围及期限。真实试点前应具备实际资料路径的处理条件；仅有用户素材授权或测试账号不替代全部必要条件。

## 6. 账号、经营与发布准备

- 提前明确真实运营、签约、发行和采购主体，项目主体持有域名、邮箱、开发者账号和云账号；不得因日本单市场就自行假定已经有日本公司或相关银行账户。
- 手机端已确定为 Android／iOS 的 Flutter APP，应准备组织账号、应用标识、签名、日文素材、隐私披露、审查账号及账号删除能力，并按最终启用的日本发布渠道核验要求。后台管理端是管理用 Web，两端共用 BackendService，不再将独立客户 Web 或承接者桌面门户列为首发选项。
- 日本客户登录、内部成员登录和管理员登录分别定权限与恢复规则；内部账号可先采用可管理的最小方案，不默认采购开放服务者 KYC 或多国短信。
- 邮件、文件、消息、模型、检查与日志服务按实际功能开通测试及生产权限。候选名称、可调用 API 和供应商的东京入口都不能直接证明已满足特定数据区域或正式运营要求。
- “承接方内部”不自动决定平台是撮合还是服务销售方，也不决定成员是雇员还是外部合同人员。对客签约、报价、收款、票据、售后与内部报酬分别明确。
- 日本业务不推导跨境付款或向中国个人结算；当前不以跨境支付开通作为前置工作。平台是否收款、采用何种国内支付方式仍待确认，确认前不承诺钱包、托管、自动结算或退款能力。
- 客户条款、隐私、素材授权、投诉、删除、AI 声明及适用经营要求，在实际主体与业务确定后按上线时现行规则复核。无收费或邀请制不自动等于可以跳过与实际服务有关的条件。

后续核验入口使用[三方服务与账号开通准备](v1-third-party-services.md)与[历史方案的官方资料索引](v1-cn-jp-localization.md)。这两个入口中的原中日采购或法规情境不能整体照搬；本次未重新开展法律或供应商调查，旧来源日期和可能变化的条件须在相应业务上线前核验。

## 7. 从开发到上线的验收门槛

| 阶段 | 可以做什么 | 必须满足的条件与证据 |
| --- | --- | --- |
| 原型与 Mock | 简中/日语手机客户及内部成员流程、双语后台合规审核与技术整理、审核通过后的大厅、内部角色、开发交付模板及账号权限设计 | 使用虚构样例；具体接单方式等未决事项不伪装为已决定；其余服务不开放，内部账号不虚标认证；去掉 Mock 界面标记不代表生产能力，release 配置门禁保留 |
| 测试环境联调 | 接入真实 API、受控第三方测试账号及授权测试人员 | 环境和密钥隔离、合成/脱敏资料；未审通过需求不可在大厅列表/搜索/详情接口泄露；身份/权限、通知、文件和故障处理验证；不接入真实生产凭证 |
| 真实邀请试点 | 指定客户与内部账号按限定容量开展真实服务 | 对该试点所需的主体、条款、资料路径、三方生产权限、人员和付款安排已明确且具备条件；先通过进入检查，不等试点结束补齐 |
| 正式发布 | 按已确认渠道和能力开放日本客户业务 | 适用手续/渠道批准已完成，日文检查、隐私披露、客服、恢复、回退、质量及容量验证通过；对外说明与真实能力一致 |

验收至少覆盖：

1. 日本客户自行注册登录，以自然语言、样例、附件提交开发需求；每项需求均留下人工合规审核与技术整理记录，审核通过后才能发布到任务大厅；无关键未翻译文本，客户不必先掌握技术术语。
2. 待审、补充中、驳回和未通过版本在大厅列表、搜索与详情均不可见；只有受控内部账号有接单权限，客户注册不能提升为承接角色；内部授权不显示为 OPC 已认证。成员变更、停用、附件和内部备注权限有效。
3. 当前开发服务至少有一条从手机提交、后台审核、发布手机大厅、手机内部接单到客户确认范围、手机交付与验收的完整样例，含软件可复现证据；两端读写同一后端业务版本，移动身份不能越权调用管理操作。具体接单机制在实现前确认；其余四条服务不得提交/接单，不以其样例作为当前上线门槛。
4. JPY、JST 与中文/日文输入及文件表现按已确认格式正确；手机与后台的简体中文、日语界面可切换，手机登录页及个人页可操作且重启恢复选择；切换不改写客户原文、业务版本、时区、金额、报价、交期或权限。语言保存专项、完整双语路径、截图和平台验证分别记录，不用旧版结果代替新变更复验。
5. 文件、AI、日志和备份符合已约定处理区域与用途；受限素材不会进入不允许的工具，模型故障可以人工继续。
6. 日本邮箱/设备和实际网络、通知拒绝、上传失败、账号恢复、投诉/删除、告警和备份恢复均有验证记录。
