# OPC V1 从 MasterGo 设计到真实 API 的实施流程

日期：2026-10-12。适用对象：项目负责人、产品设计、前端、后端与测试。当前范围以 [V1 统一方案 2.1](opc-v1-unified-implementation-plan.md) 为准。

项目负责人明确采用 **MasterGo Vibe Design 原型或效果图 → Vibe Coding 实现 Flutter + Dart／Vue 界面与 Mock 数据 → 接入真实 API**。本流程按每个完整场景分批执行，Mock 之后经过测试环境真实 API 和预发布验证，再进入生产。

2026-10-12 因 Figma Starter MCP 调用额度限制改用 MasterGo 直接创建效果图。[原 Figma 首轮 9 屏](../../Mockup/app-v1-figma/README.md)保留为历史参考；当前操作入口和进展见 [MasterGo 设计记录](../../Mockup/app-v1-mastergo/README.md)，不将历史设计视为已迁移。

当前场景为日本国内开发服务：客户注册提交，后台合规审核与技术整理，通过后发布任务大厅，内部指定账号承接。未来认证考核和其余四条服务线不作为当前必做页面；指定账号不等于逐单派单。

只设计两个产品端：APPClient 的 Flutter + Dart 手机端，包含客户和承接者完整闭环；FrontendAdmin 的 Vue.js + TDesign Vue Next 后台管理端。BackendService 是两端共用的后端源码项目，不是第三个用户界面端；不另设客户 Web 或承接者桌面门户。

## 一 每批工作如何推进

| 阶段 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| 场景定义 | 角色、页面清单、字段状态、权限和验收样例 | 本批边界明确，关键未决规则单独标识，不能把演示默认值当正式政策 |
| MasterGo Vibe Design | 视觉方向、可编辑页面、组件规范、交互连线或行为说明 | 评审本批流程、布局、日文和关键状态，保留设计版本 |
| Vibe Coding 与 Mock | 目标技术栈页面、组件、路由、表单、本地化资源、模拟场景和接口契约 | 主路径与异常可演示，Mock 与后端字段状态保持一致 |
| 测试环境真实 API | 后端和适用三方接入、鉴权、审核、发布、接单、文件与通知 | 同一用例在真实服务成立，失败、重试和权限有效 |
| 预发布与生产 | 发布包、配置、监控、验证、恢复及回滚 | 日本网络与实际目标设备通过对应验证，满足真实试点或发布条件 |

第一批进入编码时可以设计下一批。接口与技术验证和设计并行，不必等所有页面画完才开始开发；效果图、Mock 可点击和真实可用分别记录进展。

## 二 MasterGo 交接内容

效果图先确定视觉方向；准备开发的页面必须补充行为与状态。建议按基础规范、手机端客户角色、手机端承接角色、后台管理端和交接说明组织文件，每个页面有稳定编号。

| 内容 | 当前 OPC 要求 |
| --- | --- |
| 基础样式 | 颜色、字体、间距、圆角、图标、语义状态；覆盖日文、长文本和大字号 |
| 组件 | 需求表单、审核状态、技术整理、任务卡片、接单确认、源码交付、反馈与验收 |
| 角色视图 | 客户私有需求、后台审核和大厅发布分开；客户沟通与内部备注分开 |
| 布局 | 手机 APP 与桌面管理后台分别设计，注明滚动、键盘、长内容、弹窗及移动文件交付行为 |
| 状态 | 正常、空、加载、提交失败、待补充、驳回、下架、资格失效、版本冲突及已被承接 |
| 本地化 | 客户侧日文；内部语言按团队确认；币种、期限与语言分离 |
| 交接记录 | MasterGo 文件及图层链接或标识、评审版本、组件映射、资产、状态和验收场景 |

Flutter 实现手机端客户和承接者界面；Vue.js + TDesign Vue Next 实现后台管理界面，设计优先映射已有组件能力。两端按各自布局机制实现，复用业务语义与视觉规范；设计工具生成的参考代码仍需适配工程并验证。

## 三 Mock 从接口契约产生

页面通过统一数据访问接口操作业务；Mock 与真实 API 实现遵守相同契约，在应用初始化时按环境配置选择。不要把模拟数据散写在页面，也不要让每个按钮分别判断当前是否为 Mock。

两端的 Mock 使用一致的需求 ID、版本和状态样例。展示“手机提交、后台审核、手机看到发布”的联动时，使用同一个模拟服务或共享场景状态；两个各自独立的本地 Mock 不能声称已经实现联动。真实阶段两端接入 BackendService，管理与移动接口可按权限返回不同字段，但不能复制两套审核或合作规则。

契约至少约定：

- 需求原文、技术整理、审核结论和发布版本的对象关系。
- 合规与技术审核状态、大厅可见条件、账号状态、内部授权和未来认证状态。
- 字段类型、必填与可空、枚举、ID、金额币种、时间、分页和稳定错误码。
- 最终选定的接单机制、有效负责人、重复请求和版本冲突行为。
- 文件上传检查、授权链接过期、消息与 AI 作业的异步状态。

固定样例可重置并贯穿提交、审核、发布、接单、交付、验收；不能每个页面展示互不关联的演示数据。至少增加未审核需求不进大厅、审核后修改、驳回补充、普通客户尝试接单、两个成员并发承接、内部账号停用、上传失败等场景。

内部授权与认证用不同字段与文案，Mock 不制造未发生的“认证通过”。当前只允许开发服务提交；未来四条线可在设计说明标为后续，不能出现可提交但无法承接的正式入口。

开发环境明确显示 Mock 或真实测试 API，提供重置场景入口。生产构建禁用模拟拦截和场景切换；真实请求失败不能静默返回模拟成功。服务端必须重新验证审核、发布、接单授权、文件权限和版本，Mock 的成功不能替代这些实现。

## 四 第一批页面与验证链路

| 产品端及角色 | 首批页面建议 |
| --- | --- |
| 手机端客户 | 注册登录、任务查看、开发需求表单、我的需求、审核进度与补充、整理方案确认、合作与交付、修改验收 |
| 后台管理端 | 待审队列、原始需求与澄清、合规审核、技术整理、审核结论、发布下架、账号授权、内部质检、异常处理 |
| 手机端内部承接者 | 指定账号激活登录、任务大厅与详情、承接入口、我的任务、进度、文件或固定仓库版本提交、交付说明与反馈 |

接单入口在规则冻结前可展示方案草稿，不能自行选择抢单或竞标作为已确认需求。是否客户确认整理稿后才允许发布，也是单独待定规则；审核通过才允许发布则是强制条件。

推荐先用一个日文 AI 系统开发需求跑通：

1. 客户在手机端注册、提交原始描述和参考材料。
2. 管理端退回补充，客户在手机回复；后台整理技术范围并完成人工合规与技术审核。
3. 统一后端发布审核通过的版本，手机大厅看不到其他待审、驳回和下架需求。
4. 内部授权账号在手机按已定机制接单；普通客户和停用账号无法接单。
5. 客户与承接方在手机确认具体范围、交付与验收标准。
6. 承接方在手机提交约定的固定源码包或仓库版本、说明和测试材料，经后台内部检查后对客提交。
7. 客户在手机查看交付，提出修改或验收；重大范围变更进入后台复审与手机重新确认。

此链路是后续 MasterGo、Mock、API 和测试的共同样例。当前重点是开发服务，后续复用共同能力再加入认证与其他服务模板。

代码可以在外部开发工具中制作，OPC 的交付与验收操作在手机完成。手机设计需覆盖系统文件选择、上传进度、中断恢复或重新选择、重试、固定版本、报告预览或获取、演示访问、链接过期及反馈；不增加一个必须登录才能交付的 OPC 桌面门户。开发成果涉及外部运行环境的测试在实际环境完成，并将证据和结果关联到 APP 中的交付版本。

## 五 真实数据接入

| 环境 | 数据和依赖 | 检查重点 |
| --- | --- | --- |
| 本地 Mock | 合成样例和模拟操作 | 页面、状态、权限表现及契约 |
| 测试 | 真实后端、隔离数据、适用测试应用或账号 | 服务端规则、持久化、文件、消息、失败与重试 |
| 预发布 | 接近生产的配置和授权样本，明确仍模拟的部分 | 实际设备、日本网络、正式依赖、发布和恢复 |
| 生产 | 正式账号与授权业务数据 | 可用性、异常、成本、运营响应与回滚 |

接入生产不仅是替换 API 地址，还包括真实身份、权限、数据库、文件和通知等依赖。环境隔离域名、密钥、存储、回调和第三方应用，测试数据不自动导入生产；凭证按相应安全配置管理，不硬编码在客户端。

当前日本业务不证明所有供应商资料处理均在日本，真实资料接入仍需满足实际授权与处理条件。收费方式未定，不用 Mock 付款成功推导正式支付能力。

Flutter 需要在 Android 和 iOS 实际运行和设备检查；尤其验证交付上传时切后台、网络中断、重启后的状态恢复，以及重复点击不生成重复交付。手机普通身份不能调用管理操作，两端应读写同一业务版本并按各自权限展示。浏览器移动效果图不能作为 Flutter 真机通过的证据。

- Mockup 保存 MasterGo 链接、页面清单、设计版本、交接说明及必要导出；历史 Figma 资料保留并标明适用范围。
- 三个源码项目：APPClient 保存 Flutter + Dart 手机端；FrontendAdmin 保存 Vue.js + TDesign Vue Next 管理端；BackendService 保存两端共用的后端服务与 API。
- DB 保存数据库迁移；Docs 保存需求、接口、决定、测试和发布记录；不新增独立客户 Web 或承接者桌面源码项目。
- 保留“需求与用例 → MasterGo 图层及版本 → 代码页面与组件 → API → 测试记录”的关系。
- 业务状态调整同步设计、Mock、契约和实现；经评审接受的代码布局变化回写设计说明。
