| 本文建议 | 首版开放五条服务线：Vibe Coding 核心优先、数据／表格、文档、图文、短视频；每条线用低／中复杂度模板收敛，以审核供给和人工运营协助启动。 |

| 本文建议、用户未确认 | 方案 A：平台不代收付项目款，提供报价、合作确认、交付与验收记录；报价和已完成合作不代表已支付。 |
| 待决 | 是否采用方案 A，或在首版引入平台收款的方案 B；经营主体、收费方式、支付／结算安排和具体上线范围。方案 B 的资金业务由专门方案承接，本文不默认增加支付能力。 |
| 待验证 | 日本首批客户行业、真实需求频次、预算区间、日文审核供给、可接受的交期与修改次数、桌面与手机使用比例。 |

首版要验证的命题是：需求方能说明所需成果，服务者借助 AI 和明确流程完成制作，双方跨语言确认同一份交付条件，并通过版本记录完成验收和再次合作。

推荐闭环：**看服务／案例 → 提交需求 → 审核与匹配／应征 → 站内洽谈 → 报价与合作确认 → 制作 → 交付／修改 → 验收 → 评价与再次合作。**

合作确认与资金交易是两条独立链路。即使采用方案 A，内容、跨境资料访问、客服和经营安排仍须按整体规划落实；不因“不代收款”推定其他义务消失。

## 2. 五条 P0 服务线与复杂度边界

五条服务线都进入首版，Vibe Coding 为核心优先。收敛的是模板、复杂度和交付方式，不是删除用户已明确的服务方向。服务者通过对应能力检查后承接；新人可先用样例任务验证能力，不能因为注册成功就承接所有复杂度。

### 2.1 Vibe Coding：核心优先

| 项目 | 最小定义 |
| --- | --- |
| 标准模板 | 日文／中日双语展示页、小型交互工具、表单与受限流程、低／中复杂度 CRUD 模块或已有代码的明确功能改动。页面、角色、接口、集成和测试范围必须逐项限定。 |
| 输入 | 使用场景、用户角色、页面／功能清单、验收用例、目标运行环境、日文 UI 要求、设计参考；已有代码需提供获授权副本和问题复现说明。 |
| 实施前确认 | 页面／功能说明、数据字段、接口边界、测试用例与交付环境的版本；不是仅确认一张效果图。 |
| 必交成果 | 可访问的源码仓库或完整 ZIP；仓库交付标明 commit，ZIP 标明校验值，同时交付时可相互对应；README、构建／运行和部署说明、无真实密钥的环境变量样例、适用的依赖锁文件、开源依赖及许可清单、测试报告、日文 UI 与必要操作说明。 |
| 验收 | 按双方约定的用例核验功能、权限、输入校验、错误状态、数据结果和日文 UI；能够依据说明重现构建／运行。视频、截图只能辅助说明，不能代替可运行代码与用例结果。 |
| 首版边界 | 平台不执行用户上传的任意代码，不收集生产账号／密钥，不自研完整 IDE；交付在约定环境由客户或受授权人员验证，平台不为全部外部源码提供自动运行沙箱。 |
| 复杂度限制 | 多系统深度集成、核心支付系统、无限模块的整站建设和无人值守生产部署转专项评估；不得用“帮我做一个 App”作为可直接报价的完整需求。 |

测试报告需说明对应 commit／校验值、环境、用例、实际结果和已知问题。未执行的检查标记未执行，不能由 AI 生成“全部通过”。验收前的约定功能缺陷修复与新增需求分开；新增功能走范围变更。没有 UI 的脚本、无第三方依赖或无环境变量的交付，可按已确认模板记录对应项不适用及原因，但不能无说明缺项；日文说明和约定用例仍需提供。开源依赖许可清单不代表强制公开客户源码；原创代码权属与交付使用范围另在合作单明确。

源码交付采用完整 ZIP 或可访问的固定仓库版本，不能只有演示链接。双方确认合作时约定源码归档位置、保留期限、访问授权、备份责任及外部仓库失效后的交接方式；验收时需求方应能取得约定版本的完整源码。仓库链接交付不要求平台未经许可镜像客户源码；平台存储或复制源码须有相应授权，并遵守约定的访问与资料处理条件。

### 2.2 数据／表格处理

| 项目 | 最小定义 |
| --- | --- |
| 标准模板 | CSV／XLSX 字段规范、按明确规则去重、拆分合并、格式转换、已有数据的基础汇总和图表；明确输入大小、文件数和处理规则。 |
| 输入 | 样例与正式文件、字段字典、去重键、空值／异常处理要求、公式／格式保留要求、交付语言、允许使用的工具和资料访问范围。 |
| 必交成果 | 处理后文件、规则说明、处理前后行数／字段摘要、异常清单、必要的可复现步骤；客户要求脚本时适用代码交付清单。 |
| 验收 | 按样例／规则抽检并校验行列、关键统计、公式保留与异常项，原件不覆盖；不能只验收截图。 |
| 首版边界 | 不接入客户生产数据库或索取生产凭证；不把未定义规则的“清洗全部数据”直接开工；敏感数据的处理条件需先明确。 |

### 2.3 文档处理

| 项目 | 最小定义 |
| --- | --- |
| 标准模板 | 基于客户资料的 DOCX／PPTX 排版、材料结构化、会议／项目资料整理、中日文档改写及翻译校对；明确字数／页数／页型和交付格式。 |
| 输入 | 原始资料、模板／品牌规范、目标读者、语言、保留字段、事实来源、结构与页数边界。 |
| 必交成果 | 可编辑文件及约定的 PDF 预览、修改说明、待核实事项；翻译任务保留原文与最终译稿的对应关系。 |
| 验收 | 信息完整、关键数字和名称可追溯、版式与目录／页码正确、日文无乱码和明显溢出；不能只交不可编辑截图。 |
| 首版边界 | 不把无来源的事实编造为报告内容；专业判断和外部研究不自动包含，须独立约定。 |

### 2.4 商品静态图文

支持商品场景图、详情说明图和渠道尺寸适配，基于客户提供的商品素材和产品事实。模板记录数量、尺寸、格式、文本语言、风格、允许／禁止变化项与修改范围；交付成品及版本说明，源文件是否包含须提前约定。

验收检查商品形态、关键细节、文本准确性、尺寸和数量。日文文字与生成底图宜分开排版；不得把模型画出的错误日文视为合格文本。内测示例可以是“1 张场景图＋2 张说明图”，仅作配置起点，不是统一承诺。店铺代运营、销量承诺和完整品牌策划不自动包含。

### 2.5 固定规格短视频

支持已有素材混剪、基于商品图片的展示和固定镜头介绍。模板记录时长、横竖屏、分辨率、格式、字幕语言、配音、素材／音乐范围、修改次数和交期。

先确认文字脚本／镜头说明的明确版本，再正式制作；作为轻里程碑，不自动引入阶段支付。验收成片技术规格、商品一致性、字幕／配音与素材使用条件。内测可从“15 秒竖屏、3–5 个镜头、日文字幕”起步；长篇漫剧、复杂连续角色和实时直播等高复杂度内容转专项评估，不假定所有工具都能稳定完成。

### 2.6 P1、后置与共同开放条件

| 层级 | 内容 | 开放前提 |
| --- | --- | --- |
| P0 | 上述五条服务线，每线至少一套低／中复杂度模板 | 有真实样例、交付清单、验收用例、合格服务者和可处理异常的运营人员。 |
| P1 | 每线更多模板、复用合作、更多新人引导、服务者桌面工作台 | 已有模板的质量、交期和运营成本得到验证。 |
| 后置 | 高复杂度跨系统开发、长篇漫剧、本地服务、直播代运营、企业多人协作和无限范围综合外包 | 单独补齐交付、权限与异常模型，不用“其他”分类绕过评审。 |
| 后置 | 自研 IDE／图像视频编辑器、平台运行任意代码、金币广告运营、复杂会员与社区 | 有独立业务论证和实现方案。 |
| 独立决策 | 平台收款、钱包、分账、退款和结算 | 方案 B 通过评审；不可仅因有合作单就默认开启。 |

同一合作可含多个交付物，但首版选择一个主要模板并明确附属成果，避免以混合需求突破范围。模板使用 `deliverable_type` 和版本化 `template_schema` 描述字段、校验、里程碑和验收，不将全平台字段硬编码为视频时长、镜头数等单类目属性。

## 3. 用户角色、供需结构与权限

一个账户可以同时具备需求方和服务者身份。切换角色改变默认工作台，不创建重复账户。首版不建设复杂企业组织和多人审批；企业客户可由一名授权联系人操作，是否需要企业认证由经营方案补充。

| 角色 | 允许操作 | 约束 |
| --- | --- | --- |
| 游客 | 浏览公开服务、获授权案例、脱敏后的需求摘要 | 不可查看客户私有素材、联系人信息或合作记录。 |
| 需求方 | 发布和管理自己的需求、邀请服务者、查看应征、沟通、确认报价／合作、反馈、验收、评价和投诉 | 不可查看其他需求方的私有资料；不得单方改写已确认范围。 |
| 服务者 | 填写能力与语言资料、提交作品、完成能力检查，通过审核后发布服务、应征、报价和交付 | 仅能承接已开放的能力范围；作品、本人贡献与素材授权需明确；不以“会翻译”替代日文交付能力。 |
| 业务运营 | 在授权市场内审核供需内容、推荐人选、检查异常、协助补齐需求 | 不可代用户确认商业条款、验收或假冒用户发消息。 |
| 内容／日文审核员 | 根据授权查看待审稿、给出通过／修改意见、记录检查项 | 日文检查只针对可识别版本；不能把检查通过视为买方验收。 |
| 客服 | 在授权范围处理举报、超时和争议，查看必要证据并记录结果 | 访问、导出和人工更改状态需有理由和审计；方案 A 无冻结资金／退款权限。 |
| 管理员 | 配置类目、模板、角色、市场开关与系统参数 | 高权限操作审计；权限应按职责授予，避免后台人员默认看到全部文件。 |

首版支持四条供需路径：中国需求方 → 中国服务者、日本需求方 → 日本服务者、日本需求方 → 中国服务者，以及中国需求方 → 日本服务者。四种组合均属于 V1 支持范围，按实际业务、经营及数据处理条件启用；中国供给为主是运营预期，不限制双方发布需求或承接服务，也不代表所有用户和文件可无条件跨区域共享。

匹配硬条件包含交付语言、服务能力、可承接量、时间和实际服务范围；排序可考虑相关案例、响应情况与历史履约。首版采用可解释规则与人工推荐，暂不开发复杂推荐算法，也不按国籍设质量评分。

## 5. 业务对象与最小字段

以下是概念字段，不是数据库 DDL 或已经批准的 API。所有可修改业务对象应有稳定 ID、拥有者、版本、创建／更新时间及必要操作记录。

| 对象 | 最小字段与说明 |
| --- | --- |

| 举报／客服工单 Case | 对象、发起人、原因、证据、处理人、状态、处理记录、结果、申诉关联、必要访问审计。 |

重要约束：一个需求在首版只形成一个主要服务者合作；允许多份应征，选定时防止并发重复合作。一个合作单使用一种约定币种，修改币种需重新确认；参考换算不覆盖原始报价。

## 6. 状态、动作与异常

### 6.1 分离审核、展示与业务状态

| 对象 | 建议状态 | 核心规则 |
| --- | --- | --- |
| 内容审核 | 草稿 → 待审核 → 通过／待补充／不通过；另有撤回 | 审核状态不等于公开状态；重要修改重新审核。 |
| 需求展示 | 未公开 → 招募中 → 暂停 → 已确认合作／已关闭／已过期 | 关闭不删除已有会话和合作证据；暂停时不接收新的应征。 |
| 报价 | 草稿 → 已提交 → 洽谈中 → 待确认 → 已接受；分支为已撤回／已拒绝／已过期 | 旧版本确认不得接受新版本内容；重复请求不创建重复合作。 |
| 合作 | 待双方确认 → 执行中 → 待验收 → 修改中 → 待验收 → 已完成 | 双方确认同一版本才进入执行；需求方对具体成果验收。 |
| 合作异常 | 取消申请中、已取消；争议处理中作为独立标记 | 争议不抹掉原阶段；状态变更说明原因，限制矛盾操作。 |
| 实施前确认 | 待提交 → 待确认 → 需修改 → 待确认 → 已确认；新版本使旧确认过期 | 各模板定义需确认内容；代码功能／用例、数据规则和视频脚本等实质改变时重新确认。 |
| 文件 | 上传中 → 检查中 → 可用／失败／隔离 | 不可用文件不能进入正式交付或通过公开链接访问。 |
| AI 作业 | 排队 → 处理中 → 成功／失败／取消／过期 | AI 成功不等于用户已认可草稿；重试保持业务幂等。 |
| 客服工单 | 已提交 → 待补证／处理中 → 已处理 → 申诉中／已关闭 | 处理意见、证据与客户反馈可追溯。 |

### 6.2 首版必须覆盖的异常路径

1. **报价或范围变化**：关键字段变更产生新版本，失效旧的待确认；不得在对方不知情时更改价格、期限或交付内容。
2. **重复应征／重复确认**：通过业务唯一性和幂等约束处理重试；同时接受两份报价时只能产生一个有效合作，另一方得到清晰结果。
3. **素材迟交／不可用**：记录缺失项，发起延期或范围变更；不得无提示把服务者交付期限自动提前或顺延。
4. **实施方案改动**：代码功能／用例、数据规则、文档结构或视频脚本实质变化时走变更或重新确认，提示工期与费用影响；约定功能缺陷修复与新增需求区分。
5. **超范围修改**：展示原验收标准与修改范围，允许提出变更提案；未达成新约定时保留原合作记录并可请求客服协助。
6. **超时不验收**：发送提醒并进入运营跟进；首版在没有明确批准规则时不自动验收，更不能自动标记已支付。
7. **服务者退出／需求撤回**：提交原因和取消请求，记录双方处理结果；意见不一致时进入客服流程，不静默删除。
8. **屏蔽或拉黑**：限制新联系，但不隐藏在途合作、交付、投诉入口；必要沟通转为受控渠道。
9. **AI／翻译故障**：保留原文，提供手工表单与草稿编辑；基础发布、聊天和交付不依赖 AI 成功。
10. **文件故障与越权**：失败可重传，隔离文件不分发；每次预览／下载都校验权限；通知深链不绕过登录。
11. **账号关闭／内容下架**：公开展示可停止，既有合作记录按已确定保留规则处置；不进行破坏证据的无条件级联删除。
12. **资金争议**：方案 A 仅记录当事人陈述与客服处理，不提供不存在的冻结、退款或平台担保按钮；方案 B 另行设计。

## 7. AI、创作工具与人工责任

### 7.1 首版内置能力

| 场景 | 输入 | 输出 | 人工确认与降级 |
| --- | --- | --- | --- |
| 需求结构化 | 自然语言、类目、客户已有资料 | 按五类 schema 提供目标、规格、输入清单、待澄清项、验收用例草稿 | 发布前确认；预算、期限、产品事实、数据规则不自动猜测；可完全手填。 |
| 中日翻译 | 消息或结构化字段的原文 | 并排原文／译文、语言、源版本和翻译状态 | 关键条款用合作单字段确认；源文修改后旧译文过期。 |
| 方案／文案／脚本草稿 | 已确认要求、功能／业务规则、产品事实、用途和参考风格 | 软件实施说明、数据处理规则、文档大纲、文案或视频分镜等可编辑草稿 | 服务者检查可执行性、事实和授权相关输入；不得自动执行代码、发送或冒充客户确认。 |
| 检查建议 | 五类需求、实施说明、交付清单及验收标准 | 缺项、歧义、前后不一致与待人工核查项 | 不自动运行交付代码，不虚构测试通过；不代替真实用例、数据核验、日文检查和买方验收。 |

V1 不建设完整 IDE、任意代码执行服务、图像／视频生成工作台、时间轴编辑器、全自动成片系统或自动投放工具。服务者使用自选编码、数据处理、文档和媒体工具，并按平台入驻说明评估商用授权、输入资料使用条件、输出使用权、数据处理方式和地域可用性；平台接收符合合作约定的类型化交付物。平台提供这些服务类目，不等于首版必须自研其生产工具。

客户私有素材能否送入第三方创作工具，应在任务和工具使用安排中明确，不能因为“工具由服务者自己付费”就默认允许任意外传。对不允许外部处理的需求，必须在应征前显示限制并匹配符合条件的服务者。

AI 提供商选型需满足：对应市场可用、处理中日文本、草稿结构化、超时与重试、成本额度控制、可审计的区域路由与数据处理安排。供应商名称由专项选型文档确定。

### 7.2 日文质量责任

服务者可通过本人日文能力、明确的校对协作者，或试点阶段的平台日文审核完成检查。哪一种适用于本合作，在执行前明确；记录实际审核者与成本，不把机器翻译按钮等同于日文质量保证。

| 检查层 | 内容 |
| --- | --- |
| 产品事实 | 名称、型号、材质、颜色、规格和功能来自客户确认资料；未知项提交客户确认。 |
| 日文表达 | 意思准确、语气符合用途、品牌与产品术语一致，避免照搬国内收益或效果宣传话术。 |
| 软件 UI／文档 | 日文界面、校验与错误消息、日期／金额和操作说明一致；可见文字不被硬编码为只有中文；按约定浏览器和设备检查。 |
| 数据／文件内容 | 日文字段名、编码、日期与数字格式正确，文档段落／表格不乱码；译文不得改变原始数据含义。 |
| 静态版式 | 字体支持日文、无乱码、换行与标点可读、移动端显示不遮挡主体。 |
| 视频文本／声音 | 字幕与画面相符、可读时间合理；配音有时检查读音、专有名词和音画关系。 |
| 商品视觉 | 核对客户指定的不可变形态与细节，发现 AI 漂移需重做或明确反馈，不能仅靠文案审查。 |
| 最终导出 | 检查针对最终交付版本；修订后重新检查受影响项，不能沿用过期的通过结论。 |

## 8. 国际化与本地化产品要求

1. 分开保存 UI 语言、所在市场、可服务市场、沟通语言、交付语言、存储区域、约定币种与显示时区。选择日文不代表用户在日本，选择中国市场也不代表只能交付中文。
2. P0 用户侧支持简体中文与日文，重点检查注册、五类模板、报价、合作范围确认、实施方案、交付、验收和异常提示。后台可先用中文界面，但必须正确处理日文内容和对应市场资料。
3. 日本需求输入不强制中国手机号、身份证格式和中文姓名规则。具体身份验证由经营与第三方方案决定，不在 UI 中预设错误身份模型。
4. 日本服务文案、案例、通知、客服窗口与术语单独维护。内测应有日本需求侧可联系的负责人及可执行的服务时间安排。
5. 合作期限是明确时间，显示时区；不只保存“明天上午”。假期与工作时间按服务者排期和双方约定，不机械套用国内工作日。
6. 单笔报价保存原币金额；人民币与日元显示规则分别配置。参考换算显著标记参考，不作为最终结算承诺。
7. 跨语言的价格、工期、修改范围和验收标准，双方确认同一个结构化版本。原文改变后旧译文应过期；无法可靠表达时进入人工澄清。
8. 客户素材、内部交付和公开作品是不同可见范围。完成合作不等于授权发布案例；“做同款”不得带出客户私有文件或联系人信息。

## 9. 审核、客服与后台可执行动作

P0 采用人工主导、规则辅助的运营方式。自动检查可提示缺项或问题，不在未定义审核标准时直接用模型替代全部人工决策。

| 队列 | 输入与操作 | 输出 |
| --- | --- | --- |
| 服务者审核 | 查看资料、作品、本人贡献、工具使用说明、类目样例与日文检查方式；通过／补充／拒绝 | 类目资格、原因与复审记录。 |
| 服务／案例审核 | 检查描述、规格、授权和案例来源；上架／退回／下架 | 公开状态、版本和操作记录。 |
| 需求审核 | 检查真实交付目标、素材、预算／期限表达、交付语言和可服务范围；退回补齐或发布 | 合格需求、缺项说明。 |
| 匹配协助 | 查找满足硬条件的候选、发起正式邀请、跟进无人应征 | 可解释推荐和邀约记录，不假冒用户接受。 |
| 日文／交付检查 | 按模板检查指定实施方案或交付版本，确认代码／数据／文档／媒体所需证据，记录问题与责任人 | 检查结果及未执行项，必要时退回修改；后台不自动运行任意上传代码。 |
| 合作异常 | 处理未响应、超时、取消、范围争议，联系双方补证 | 可追溯处理记录，不改写原始证据。 |
| 举报与申诉 | 按对象查证、限制违规内容／账号、反馈原因、受理申诉 | 处理状态、理由与纠正记录。 |
| 模板与配置 | 类目、规格、修改范围、通知文案、市场开关、AI 额度 | 配置版本与审计；旧合作使用原确认快照。 |

上线前需要可值守的审核、日文检查与客服责任人；工作量、服务时间和升级联系人由运营方案填写。不能只做前台入口而没有可处理的后台动作。

## 10. 冷启动和业务指标

邀请首批真实日本需求方及国内需求方，组织经过能力检查的中日服务者，在限定服务包中完成合作。每个开放类目至少有模板、授权样例、验收清单、可接单服务者和异常处理负责人。

首版北极星候选指标为“有效需求形成合格交付的数量与比例”，不是注册数、聊天条数或 AI 调用次数。具体数值目标应在试点需求量、客单价和运营产能明确后设定，不把本文示例当行业基准。

| 指标 | 建议口径 | 分组 |
| --- | --- | --- |
| 有效需求数 | 通过审核、具备可执行范围且非重复／测试的需求 | 需求市场、服务类别。 |
| 首次合格应征时间 | 发布到首份满足硬条件和基本报价字段的应征 | 无人应征单独统计，不能从分母剔除。 |
| 合作确认率 | 观察窗口内形成双方确认合作的有效需求／到观察期的有效需求 | 国内、日本当地、跨境合作。 |
| 脚本一次确认率 | 无修改即通过的首次脚本／已完成首次脚本审阅的合作 | 视频类；未审阅单独统计。 |
| 首次交付验收率 | 首个正式交付版本被接受的合作／已完成首次交付审阅的合作 | 五条服务线、复杂度、语言。 |
| 代码／数据／文档质量 | 代码用例通过及构建可复现情况、数据校验差异、文档事实／版式问题 | 只统计实际检查；未运行用例单独标记。 |
| 按时交付率 | 在双方有效约定期限内提交合格可用版本的到期合作／到期合作 | 展示原期限和经同意的变更，不允许静默改期美化结果。 |
| 修改与质检成本 | 平均修改轮次、日文问题率、商品一致性问题率、审核工时 | 类目、服务者资格、工具使用方式。 |
| 投诉／客服介入率 | 有客服介入的合作及原因／合作总量 | 内容、沟通、交期、范围、外部付款陈述等。 |
| 复购率 | 已完成首次合作的客户在固定观察窗内再次确认合作的比例 | 按首单完成时间形成同龄分组。 |
| AI 使用与成本 | 成功作业、草稿采纳率、失败率及每次有效合作分摊成本 | 场景、市场、供应商；成本预算另定。 |

方案 A 下只能统计“已确认合作报价金额”等明确口径，不能将其称作已支付 GMV 或平台实际结算额。外部付款自述应标明未由平台核验，不与合作验收状态混淆。

## 11. V1 验收场景

以下 12 项为后续测试设计入口，尚未执行。每项 PRD 应补充页面、接口、权限、异常和测试数据；不能把“文档已写”当作功能通过。

| ID | 场景与前置条件 | 可观察的通过条件 |
| --- | --- | --- |
| OPC-V1-AC-01 | 日本需求方用桌面浏览器、中文需求方用 App 分别完成核心流程 | 对应语言下可独立完成需求、沟通、确认和验收；日本客户不被强制安装 App；时区／币种无错用。 |
| OPC-V1-AC-02 | 客户从公开案例点击“做同款” | 表单继承公开规格并可修改，保留来源；没有原客户私有素材、联系人或内部消息；产品事实需客户补充确认。 |
| OPC-V1-AC-03 | 五条服务线均有标准模板，新服务者提交资料并应征 | 每线至少能发布并完成一套低／中复杂度模板；对应资格未通过不能承接受限需求；语言硬条件不满足时不推荐；Vibe Coding、数据／表格、文档没有被后置。 |
| OPC-V1-AC-04 | 客户用 AI 补齐需求、服务者生成软件方案／数据规则／内容脚本草稿，中日译文发生失败或源文更新 | 所有结果是可编辑草稿；不自动执行／发送／确认；失败保留手工入口与原文；过期译文被明确标记。 |
| OPC-V1-AC-05 | 两位服务者同时提交报价，客户端重试接受操作，随后修改价格或日期 | 只产生一个有效主要合作；双方确认同一版本才执行；条款修改撤销旧待确认，不静默覆盖已确认记录。 |
| OPC-V1-AC-06 | 代码合作确认功能／用例，视频合作确认脚本，数据合作确认规则；客户要求变更 | 同一轻里程碑支持模板化内容；反馈与版本可追溯，实质变更重新确认；约定缺陷修复不被当作新增功能，新增内容也不自动算免费修改。 |
| OPC-V1-AC-07 | 每条线各提交一份真实交付，并故意遗漏一种必要成果 | 代码按已确认模板校验源码、commit 或校验值、README、部署说明、env 样例、依赖锁、许可和测试报告；适用的必交项缺失时不能确认完整交付，不适用项记录原因；按用例及约定日文 UI 验收。数据按规则与行数／异常核验；文档检查可编辑稿与版式；图文／视频按规格及日文检查；旧检查不自动覆盖新版本，截图或视频不能代替代码用例结果。 |
| OPC-V1-AC-08 | 客户对首次交付提出修改，再提出超出原范围的新要求 | 普通修改关联原验收项与版本；超范围要求生成变更提案，未接受不扩大原义务；旧文件和意见仍可查。 |
| OPC-V1-AC-09 | 文件上传中断、隔离失败，其他用户获得文件链接；服务者交付代码包 | 可重试但无空交付／重复记录；文件不可用时不能验收；越权访问失败；平台不自动执行上传代码，不索取生产凭证，env 样例中不应包含真实密钥。 |
| OPC-V1-AC-10 | 发生超时不验收、服务者退出、客户拉黑或合作争议 | 出现对应提醒、取消／客服入口及明确处理记录；不自动验收或标记付款；拉黑不抹去在途合作和投诉证据。 |
| OPC-V1-AC-11 | 不同权限的运营人员处理中国／日本合作；客户完成合作但未授权案例公开 | 权限外私有材料不可访问；必要访问和导出留审计；已完成成果不自动公开；下架不破坏合作记录。 |
| OPC-V1-AC-12 | 按方案 A 完成合作并在后台查看指标与客户端状态 | 页面仅显示合作／验收完成，不显示平台已收款或已支付；报价金额不计为已支付 GMV；评价仅来自真实完成合作，指标按市场和类目可追溯。 |

若最终采用方案 B，AC-12 需替换为经过评审的支付、回调、退款、对账、结算和异常验收集合；不能在此场景上简单加一个“支付成功”按钮。
