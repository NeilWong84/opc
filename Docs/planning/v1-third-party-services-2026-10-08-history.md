# OPC V1 三方服务、账号开通与采购准备

> 状态：评审草案；编制与官方资料核查日期：2026-10-08。本文是产品需求、技术选型和实施准备的输入，不代表供应商已选定、服务已采购或账号已开通。
>
> 市场前提：中国与日本；设计支持中国需求→中国服务、中国需求→日本服务、日本需求→中国服务、日本需求→日本服务四种组合，重点验证日本需求→中国供给。跨境实际开放受主体、资料处理与具体业务条件制约。**Vibe Coding、AI 数据与表格处理、AI 文档处理、AIGC 图文、短视频为五条首版核心服务**，Vibe Coding 是重要业务方向。客户端沿用 Flutter + Dart，管理端沿用 Vue.js + TDesign Vue Next；后端、主云和运营主体仍待决策。

## 1. 首版采购边界

**实际资金方案尚未确定**；本文仅以建议的 **V1-A：撮合 + 合作交付记录，平台不代收代付** 作为采购规划基线。首版围绕发布需求、浏览服务与案例、匹配、双语洽谈、确认合作、提交作品、反馈修改、验收记录和投诉处理采购必要服务。合作记录不等于支付订单，双方标记的付款状态也不是平台已核验的银行入账。

**V1-B：平台收款、退款或向创作者结算** 是条件增量。只有在平台主体、付款国、创作者所在国与身份类型、收款账户、资金流、服务类别、支付机构准入及商店规则得到确认后，才进入开发和采购承诺。不能仅靠接入支付 SDK 把 V1-A 变成可跨境结算的交易平台。

平台内 AI 首版覆盖四个通用用途：**需求结构化、中日辅助翻译、方案与说明草稿、验收清单建议**，共用文本模型能力；方案与说明草稿可包含脚本、文案和交付说明。AI 质检仅辅助检查已授权可读内容和提出验收建议，不执行未知代码、不自动确认验收、不担保成果通过。服务者可使用符合所在地区支持条件、经过自身商用授权检查的外部 AI 编程、办公、图片或视频工具完成生产。OPC 不在首版建设托管代码执行平台、多模型视频生成平台、算力市场、会员积分或 AI 代币钱包；服务者使用的外部工具不自动成为 OPC 集成供应商。

优先级定义：

- **P0**：对应首版上线市场和功能必须可用，缺失时应关闭相关入口或暂停该市场上线。
- **P1**：有真实使用数据或运营需要后增加；不阻塞首版基本合作流程。
- **条件项**：仅在采用 V1-B 或开放特定能力时启动；不能作为默认已选范围。

## 2. 不能合并成一个字段的区域信息

国际化采购表和系统设计至少分别记录以下信息：

| 维度 | 示例与作用 |
| --- | --- |
| 产品市场 `market` | 中国、日本；决定可售服务、商店渠道、协议与运营规则 |
| 界面语言 `locale` | `zh-CN`、`ja-JP`；不得决定账户归属或付款资格 |
| 用户常住地 / 企业登记国 | 影响准入、身份核验和合同，不由 IP 自动认定 |
| 运营 / 签约主体 | 与云、短信、IM、应用商店和支付机构签约的真实主体 |
| 服务账号所在站点 | 国内站、国际站可能有独立账号、合同、计费与实名认证要求 |
| 服务部署区域 `data_region` | 数据实际存储与处理位置，不能由“全球可访问”推导 |
| 业务协作域 | 国内合作、跨境合作使用哪个聊天、文件和协作记录归属域 |
| 付款国、商户国、收款人国 | 三者必须分别核验；收日本银行卡付款不等于能向中国个人打款 |
| 计价 / 收款 / 结算币种 | `JPY`、`CNY` 分开记录；金额与币种绑定，不能只用 `¥` |

切换日语不能将中国用户资料自动搬到日本；从日本访问也不能被当作已取得跨境处理或收款资格。账号注册、IM、翻译、AI、对象存储、错误日志都要进入数据流清单。

## 4. 已核实的供应商限制及其设计影响

### 4.1 短信、邮箱和推送

腾讯国内短信的签名申请区分国内/国际、支持证明类型和实名资质，开通不能仅创建 API key。国内短信套餐不可用于国际短信；日本路线需独立确认模板、送达和计费分段。[腾讯短信签名 API](https://cloud.tencent.com/document/product/382/41146)、[腾讯短信价格说明](https://cloud.tencent.com/document/product/382/8414)

建议中国侧以 +86 验证码为首选、日本侧以邮箱为首选，并允许符合账户策略的备用找回方式。手机号统一保存国际区号和标准化号码；邮箱不能作为跨系统唯一主键。邮件需要 DNS 身份验证和发送质量运营；SES 新账号进入正式发送还需检查生产权限与配额。[SES 邮件身份验证](https://docs.aws.amazon.com/en_en/ses/latest/dg/email-authentication-methods.html)、[SES 创建及验证身份](https://docs.aws.amazon.com/ses/latest/dg/creating-identities.html)

FCM Android 客户端依赖符合要求且装有 Google Play Store 的设备，因此 OPC 不能把 FCM 当作国内 Android 的唯一推送通道。腾讯推送文档也明确各厂商需要注册应用并配置自己的凭证。日本 Android 使用 FCM 仍要保留应用内消息中心，通知送达不是消息已读。[FCM Android 前置要求](https://firebase.google.com/docs/cloud-messaging/android/get-started)、[腾讯厂商推送配置](https://trtc.io/document/60547?menulabel=core+sdk&platform=android&product=push)

推送默认仅含“有新的合作消息”等摘要和不透明业务 ID；不要向厂商通道放入客户完整需求、私密报价、附件地址或证件信息。点击通知后仍由业务 API 校验用户权限。

### 4.2 IM：同一品牌并不等于跨区互通

腾讯 Chat 官方资料提供 Flutter SDK、全球接入能力和多地数据中心选项，但**不同数据中心的用户不能互通**。全球接入点与消息存储区域也不是同一概念。消息历史默认保留期与付费扩展影响成本，必须按采用套餐重新确认。[Chat 能力概览](https://trtc.io/document/33515?menulabel=core+sdk&platform=flutter&product=chat)、[控制台和部署区域说明](https://trtc.io/document/66875)、[数据中心概览](https://trtc.io/document/33513)

首版不应先建立中国/日本两个互不互通的 `SDKAppID`，再假设前端可以直接发起跨区会话。技术验证阶段必须在以下路径中选定一个：

1. 跨境合作使用一个明确归属的数据中心和会话应用，双方获授权后加入；将跨境访问、存储、告知及数据处理纳入设计。国内合作是否另有区域应用，按数据评估和业务需要确定。
2. 如果统一会话域不符合已确定的数据约束，改选具备相符跨区能力的产品，或缩小首版为业务内消息线程并自行负责投递、未读和补拉；仍必须具备双方沟通能力。

不建议首版临时开发两个 IM 产品实例间的双向消息中继：消息顺序、重复、撤回、删除、举报取证和权限都会增加复杂度。技术验证必须使用中日真实网络及两国账号，而不是只运行供应商 Demo。

合作范围、报价版本、验收状态和附件版本应以 OPC 业务记录为准；聊天云历史保留期不能决定合作记录何时丢失。会话举报的证据保存范围另定，不默认永久保存全部私人聊天。

### 4.3 素材与交付：跨境可访问不等于可无限复制

客户品牌素材、图片、脚本、音视频、办公文件、数据集、源代码与交付说明是本项目核心数据。存储策略必须区分：公开案例、私有需求素材、合作交付物、用户身份材料、系统日志。候选对象存储支持多个区域，应在开户和创建桶时明确位置；不能依赖 CDN 自动解决数据归属。[腾讯 COS 区域文档](https://www.tencentcloud.com/document/product/436/6224)

建议文件记录至少包含 `owner_market`、`storage_region`、`visibility`、`cooperation_id`、`version`、`retention_policy`、授权共享范围和删除状态。跨境合作只共享双方完成服务所需的材料，不建立客户全部资料的默认跨境镜像。

首版实现私有素材短期签名下载、按参与者授权、图片/视频预览与原件分离、分片上传、断点续传、大小/类型限制和病毒检查。公开案例需单独取得展示授权；合作已验收不等于允许用于营销。采购测试至少覆盖两国上传、下载和失效链接，记录成功率及超时分布后再确定文件上限。

**Vibe Coding 交付最低要求**：必须有客户可靠可取用的固定源码版本，可采用“完整 commit SHA + 客户有权限的仓库 + 约定归档方式”，或“完整源码 ZIP + 哈希”。另按交付范围附 README、环境变量名称示例、依赖/许可清单、部署与回滚说明、服务者测试记录、版本与验收截图，以及约定的演示链接。仓库由客户/服务者通过 GitHub、GitLab 或经双方网络验证的 Git 服务管理；明确访问期限、归档责任、仓库停用后的取用安排。OPC 保管源码副本必须获得相应权限许可，不能要求所有客户必须向平台镜像 ZIP，也不能仅凭演示 URL 或浮动 `main` 分支认定源码已交付。平台不索取仓库长期凭证。GitHub 官方指出分支与标签可以移动，特定 commit 才能固定内容。[GitHub 源码归档说明](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives)

**预览站约定**：日本客户的演示站候选为 AWS Amplify Hosting，或已选主云的日本区域部署，由服务者或客户自己的隔离账号负责；Amplify 可托管 Web 应用并提供分支预览及自定义域名，但其 CDN 分发不代表所有数据仅留日本。应用后端/数据库区域另行确定。报价中必须列明预览有效期、域名/云资源/API 用量由谁支付、生产账号最终归属、移交后由谁维护。OPC 首版只保存已授权演示链接、版本和验收记录，不为用户代码提供宿主机，不执行其安装脚本、构建脚本或工作流。[Amplify Hosting 能力](https://docs.aws.amazon.com/amplify/latest/userguide/welcome.html)、[自定义域名要求](https://docs.aws.amazon.com/amplify/latest/userguide/custom-domains.html)

**基础安全检查与可选 SaaS 分开**：P0 必须有文件隔离、类型/大小限制、压缩包展开限额与路径校验、恶意文件检测及疑似凭证发现后的阻止共享/提醒。源码静态秘密扫描可以评估 Gitleaks 等工具，不要求购买代码托管商高级安全套餐，也不能把扫描通过表述为“代码无漏洞”。不自动运行陌生项目；客户/服务者在自己的测试环境按验收清单验证功能，平台留存报告与双方反馈。[Gitleaks 官方项目](https://github.com/gitleaks/gitleaks)

平台扫描仅覆盖已获授权接收的交付包；采用客户仓库交付且未授权 OPC 保管源码时，由约定责任方执行检查并提交结果摘要，OPC 不为扫描而默认克隆或镜像私有代码。检查证据需说明执行方、版本和范围，不能冒称为平台已独立复核。

**办公处理交付**：表格交付需原件、结果、字段/公式或转换说明、抽样核对结果；文档需可编辑源文件与 PDF/图片预览；数据需格式、编码、字段字典和校验摘要。宏、外链、可执行脚本不默认运行，CSV 导出需处理公式注入风险。首版可要求服务者提供预览副本，降低自动转换采购复杂度；Office 转 PDF、在线表格编辑、OCR、复杂数据抽取和视频转码 SaaS 仅在真实需求证明必要后接入。自动预览的转换任务同样必须隔离资源并更新解析器，不能在主业务进程处理不可信文件。

### 4.4 AI 与翻译：按处理区域选择，保留人工控制

百炼各地域有独立的接入域名、API key 和模型列表，不能混用。国内可用的中国内地区域候选与日本侧推理服务应分别配置，不能把国内输入默认转发给海外模型作为故障兜底。[百炼 API key 与地域](https://help.aliyun.com/zh/model-studio/get-api-key/)

AWS Bedrock 官方区分区域内、地理范围和全球推理，东京 endpoint 本身不能证明所有模型都只在东京处理。日本首版选择模型时优先验证区域内推理；若改用跨区域推理，重新记录实际允许处理的区域。不开通不明确数据路径的自动全局路由。[Bedrock 各模型区域与推理范围](https://docs.aws.amazon.com/bedrock/latest/userguide/models-region-compatibility.html)

Amazon Translate 提供东京端点，可作为日本侧中日翻译的候选；中日语言质量、术语和任务适配仍需 OPC 自己评测。[Amazon Translate 端点](https://docs.aws.amazon.com/general/latest/gr/translate-service.html)

所有 AI 调用由后端统一管理：任务白名单、模型版本、输入摘要、费用和超时限额、故障降级；客户端不得持有供应商私密 key。需求结构化失败时保留普通表单；翻译失败时显示原文和可重试状态；方案/说明草稿或验收清单建议生成失败，不阻断发布需求、上传交付物和人工验收。AI 辅助质量检查不运行未知代码，也不代表平台对作品质量或测试通过提供担保。

日本与中国服务者可以使用不同外部生产工具，平台以交付规格和验收标准统一结果。不要要求中国服务者必须使用其所在地不支持的海外模型、代码助手或账户，也不提供绕过地区限制的网络方案。客户源代码、数据库和素材能否提交给某工具，需要与客户授权、供应商数据用途及地区条件一致；不得索取客户 AI 账号密码代跑任务。OPC 内置模型对外部工具没有强制绑定。

中日合作记录保存原文、译文、源/目标语言、译文生成时间和人工确认状态。报价、交付时间、修改次数、权利范围、取消条件必须由双方明确确认，不能因机器翻译生成而自动生效。日本客户可见的服务标题、案例说明、客服模板以及最终日文文案，应有日语人员审校；这属于 P0 运营能力，不是买一个翻译 API 就完成。

### 4.5 审核与监控：不能假定多语言覆盖

腾讯文本内容安全官方 FAQ 当前明确列出中文、英文；不能把这一接口宣传为已完成日文审核。把日文翻译成中文后审核可作为补充线索，不能替代对日文原文语境的审核与申诉复核。[腾讯文本语言支持](https://cloud.tencent.com/document/product/1124/64679)

面向公开发布的需求、服务、案例和创作者资料，采用可追踪的审核状态；首版样本较少时，日本内容可先经过人工审校发布。原始素材和私人消息的检测范围应基于既定目的与规则，不为方便而送入额外第三方。图片/视频供应商能力与语言能力分别验证。[腾讯内容安全产品范围](https://cloud.tencent.com/document/product/1124/)

Sentry 提供 Dart/Flutter SDK，可进入崩溃方案候选；采用托管还是自建、日志存储区域、事件保留期、原生符号上传和 SDK 隐私声明仍需评审。首版关闭会话回放和正文抓取；不要为了排查错误完整记录用户需求与生成内容。[Sentry 官方 Flutter SDK](https://github.com/getsentry/sentry-dart)

### 4.6 应用商店与账号主体

Apple 组织注册要求包括法律实体、D-U-N-S、签约授权、组织域名邮箱和可公开访问的网站。Google Play 组织账号同样要求 D-U-N-S。应由 OPC 真实主体注册和保管，不使用外包人员个人账号发布正式应用。[Apple 注册要求](https://developer.apple.com/help/account/membership/program-enrollment/)、[Google Play 账号类型](https://support.google.com/googleplay/android-developer/answer/13634885?hl=en)

中国国内投放需将 APP 备案列为发布前置事项，具体主体、接入商、服务类别与其他适用资质由合规工作流核定；日本 App Store/Google Play 的上线不替代中国要求。[工信部 APP 备案通知](https://www.miit.gov.cn/jgsj/xgj/wjfb/art/2023/art_dd783a581c9644a4aee10afa582811db.html)

正式 Bundle ID、Android application ID、签名主体、云环境和渠道列表应在申请推送、社交登录与发布账号前确定。建议共享 Flutter 业务代码，通过环境及市场配置管理供应商接入；是否拆中国/日本商店应用包以实际 SDK、备案、主体和上架差异评审，不直接等同于两套产品代码。

## 6. 凭证、环境与账号台账

### 6.1 环境隔离

- 开发、测试、生产分别有独立账号项目或至少独立应用、数据库、桶、API key、IM `SDKAppID`、发信身份与通知目标；共享根账号时仍需不同权限角色和预算标签。
- 测试仅发送到白名单号码/邮箱/设备；不能用生产用户文件评测模型或测试审核。
- 日本/中国路由由服务器检查账户与业务域授权；客户端传入的 `market` 不能直接授权访问另一区数据。
- 密钥保存在部署平台的 Secret 管理服务中；代码库、设计稿、截图和文档只记录凭证名称、归属与轮换时间，不写密钥值。
- 客户端可配置公开 AppID 和必要的端侧标识，服务端签名密钥、邮件凭证、支付私钥、AI key、KMS 权限都留在后端；临时上传令牌按用户、路径、时效和操作范围限制。
- webhook 校验签名、时间与重放；写入去重记录后更新业务状态。供应商回调重试不得造成重复通知、重复审核或重复付款。

### 6.2 账号台账建议字段

`service`、优先级、用途、签约主体、国内/国际站点、账号所有者、采购负责人、技术管理员、财务联系人、环境、区域、实际数据类别、保留期、DPA/合同位置、应用标识、密钥引用名称、计费方式、预算/告警、配额、到期日期、退出/删除办法、状态、验收报告链接。

状态建议使用：未评估 → 材料准备 → 已提交申请 → 获准测试 → 联调通过 → 获准生产 → 已上线；拒绝/补材料/暂停单独记录。每项负责人可由同一人兼任，但不可无人负责。

| 隐私与日志 | 拒绝非必要授权后基础流程可用；SDK 初始化按既定同意规则控制；日志无验证码、token、私有 URL 和客户素材 |
| 崩溃与恢复 | Flutter/原生崩溃符号可还原；告警有人接；供应商故障可关闭相应能力；备份恢复通过抽样实际执行验证 |
| 发布 | 中日真机、系统版本、中文日文长文本、相册/通知权限、注销入口、商店审查账号；iOS 构建具备 macOS/Xcode 或合适云构建资源 |

具体成功率和延迟门槛由产品/技术结合小样本基线确定后写入非功能需求；不要把供应商宣传 SLA 直接当作 OPC 端到端 SLA，也不要宣称尚未测试的指标已达标。

### 7.2 成本核算口径

预算至少分人民币、日元及供应商实际账单币种；换算汇率只用于内部预算，保留日期和来源，不改写订单约定金额。

| 成本类别 | 主要变量 |
| --- | --- |
| 固定/基础成本 | 云主机、托管数据库、备份基线、域名、开发者账号、基础 IM/推送套餐、监控、企业邮箱、双语客服排班 |
| 身份与通知 | 月注册人数 × 验证次数 × 失败/重试系数；按国内/日本短信分别估算；邮箱发送、退信处理、防刷损失 |
| 媒体 | 活跃合作数 × 每单原始素材/版本/成品容量 × 保留期；中日下载次数、CDN、跨区和公网出口；视频预览转码与审核分钟 |
| AI / 翻译 | 每次需求抽取、翻译、草稿输入输出量；长对话增量翻译、模型重试、缓存命中；不以“每个用户一次”低估 |
| 审核与客服 | 内容发布量、日语校对时长、人工升级率、投诉和修改争议工单；这是跨境业务的核心成本 |
| 监控与安全 | 日志吞吐和留存、错误事件/性能采样、WAF、扫描、密钥管理、值班和恢复演练 |
| V1-B增量 | 收款/跨境/换汇/打款费、拒付和退款处理、保证金/延迟结算占款、对账、税务及商户/创作者核验 |

立项时做保守、基准、增长三档业务量测算；每家供应商确认免费期、最低消费、超额单价、计费币种、税费、额度提升时效和退出数据导出。免费额度到期不是新的业务收入来源，不能靠假定长期免费支撑方案。本文不提供未经账户报价确认的固定价格承诺。

## 8. V1-B 支付条件增量

### 8.1 四条资金路线必须分别判断

| 付款方 → 服务提供者 | 可评估的方向 | 当前不能假定的内容 |
| --- | --- | --- |
| 中国需求方 → 中国创作者 | 微信支付/支付宝适配的商户或服务商/平台方案；支付机构审核后确定收款与结算关系 | OPC 普通商户号天然可为任意个人代收、分账或提供托管 |
| 日本需求方 → 日本创作者 | 日本符合准入主体 + 日本收单/平台支付方案；Stripe 可作为候选 | 仅开日本普通收款账户就等于批准 marketplace、卖家入驻和分账 |
| 日本需求方 → 中国创作者 | 由明确支持相应服务贸易和收款人类型的持牌支付/银行合作方形成完整链路；收单、换汇、付款可能是不同服务 | 日本 Stripe 收款 + 中国银行卡号 = 已可结算；也不能承诺所有中国自然人均可收款 |
| 中国需求方 → 日本创作者 | 与上一方向分开核验付款目的、商户与收款人类型、允许资金流和银行材料 | 反向路线一定对称可用，或海外微信/支付宝收款代表双向跨境付款均可用 |

如果 OPC 实际自行签约承接客户项目，再向创作者采购服务，其角色、责任与税务将不同于纯撮合平台；必须在产品协议和业务模型中明确，不能只为绕过支付限制而在代码中改变“商户”字段。

### 8.2 Stripe 已核查结果

- Stripe 官方全球开户支持范围列有日本，不能将其理解为中国大陆企业也能按相同方式直接开户；主体所在地与银行、业务准入需要按账户确认。[Stripe 全球支持范围](https://stripe.com/global)
- 当前 Connect 自助跨境打款文档列出的平台及互转范围为美国、英国、欧洲经济区、加拿大和瑞士；日本平台向中国创作者付款不在这个自助范围内。官方建议对于范围外需求联系销售讨论，不能在尚无批准时写成可行结论。[Connect 跨境打款](https://docs.stripe.com/connect/cross-border-payouts)
- 同一文档列出的 Global Payouts 平台方范围为美国、英国；不能用这个产品名称直接解决日本或中国 OPC 主体的付款资格。文档列出的产品行为及责任也不同于 Connect，后续若范围变化须重新核验。[Global Payouts](https://docs.stripe.com/global-payouts)
- Stripe 上微信支付和支付宝的日本商户收款支持，不等于日本消费者普遍使用这两个钱包，也不等于中国创作者结算能力。两个支付方式的 Connect 支持、产品组件、退款期限和审批条件分别不同。[Stripe 微信支付](https://docs.stripe.com/payments/wechat-pay)、[Stripe 支付宝](https://docs.stripe.com/payments/alipay)

以上为 2026-10-08 公开资料快照，不替代供应商对 OPC 真实业务的账户审批。V1-B 技术文档应附供应商针对该资金路径的书面答复，而不只附市场宣传页。

### 8.3 V1-B 开通前必须得到的答案

1. 谁与客户签合同、谁开票或出具账单、谁是收单商户、谁承担退款和拒付？OPC 是中介还是服务销售方？
2. 支付服务支持哪个国家的法人，是否要求当地银行、地址、代表人、税号或受益人材料？不得推定一定需要或不需要日本公司。
3. 接单者允许中国个人、个体户、企业以及日本个人/法人中的哪些类型？KYC/KYB 材料、更新期限和失败处置分别是什么？
4. 哪些币种用于报价、客户实付、商户入账和创作者到账？何时锁定汇率、谁承担汇差及退款后的汇差？
5. 项目款是否可延迟支付、如何做分期或里程碑、是否可以合法支持所谓“担保/托管”？没有明确产品与法律依据时，不使用这些承诺。
6. 退款、部分退款、拒付、负余额、付款后创作者封禁、账户审核失败、跨境退汇时资金回哪里，由谁出资？
7. 平台佣金与创作者报酬如何分别确认；日本消费税/发票与中国税务、服务贸易证明等需要哪些流程？交由适格专业人员结合主体确认。
8. App 中购买定制数字成果、订阅、AI 使用额度等分别适用哪类商店支付规则？没有商店规则评审结论前，不假定可自由挂外部支付按钮。
9. webhook、退款 API、对账账单和打款状态是否完整；是否允许先沙箱后受控真实测试；支持/冻结处理的响应机制是什么？

采用 V1-B 后还需增加支付状态、退款状态、创作者结算状态的独立状态机，业务验收不能直接等于付款已到账。账务采用可追溯分录和幂等处理，不能用“余额”单字段累加减覆盖资金历史。
