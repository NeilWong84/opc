# OPC V1 统一落地整体方案

版本：2.7 客户确认后自主承接版  
日期：2026-10-26  
适用对象：项目负责人、产品设计、研发、测试、日本业务及运营

**当前首版面向日本需求、日本国内承接，只开放“开发（AI 开发系统）”服务。客户注册登录后提交需求，后台完成合规审核和技术整理，审核通过后才能发布到任务大厅。承接方当前由内部指定系统账号接入，未来再引入考核及正式 OPC 认证准入。**

主流程：**注册登录 → 提交原始需求 → 后台合规审核与技术整理 → 审核通过并发布大厅 → 授权承接者与客户沟通范围条款 → 客户确认 → 该承接者一键承接并执行 → 交付与修改 → 客户验收**。客户确认具体发布版本和提案条款，承接时服务端再次复核归属、授权和版本。

**首版确定为手机端和后台管理端，共用统一后端服务。** 手机端使用 Flutter + Dart，覆盖客户与承接者完整闭环；管理端使用 Vue.js + TDesign Vue Next，处理审核、技术整理和运营。独立客户 Web 与承接者桌面门户不属于本版。

本版替代此前跨境、五类同时上线的首版范围。[旧 1.1 版](opc-v1-unified-implementation-plan-v1.1-history.md)保留供追溯。2026-10-16 先实现 Python + FastAPI + psycopg 后端，随后按用户要求将 APPClient 接入真实 API，并在独立持久 PostgreSQL 初始化演示数据。2026-10-22 FrontendAdmin Vue 页面也已接入真实管理 API，包含独立登录、需求审核发布、项目交付、成员权限与审计；无接口的工单等能力明确未开放。见[后台联调说明](../development/frontend-admin-api-integration.md)。[联调说明](../development/app-backend-integration.md)和[验证记录](../testing/app-backend-integration-2026-10-16.md)记录本轮结果。文档版本不表示生产部署、资金模式或全部外部服务已经落实。

## 2 产品与服务范围

客户不需要懂技术。需求入口以目标、使用场景、当前困难、参考案例、期望时间及可提供材料为主；预算可询问区间。不要求客户预先选择编程语言、框架、数据库或专业验收指标，不确定的内容允许标记为“需要协助”。

首批开发任务建议先限制复杂度，选择能够定义清楚功能、交付物和验收标准的 AI 系统或应用开发场景。具体是否支持新建系统、已有系统功能改造、AI 接入或自动化工具，由首批模板决定；不因“开发”两个字就承诺承接任意大型系统。

| 当前开发服务需整理的内容 | 结果 |
| --- | --- |
| 目标与使用者 | 谁用、解决什么问题、业务上期待什么结果 |
| 范围与排除项 | 本次功能、明确不包含的工作和外部依赖 |
| 技术与资源条件 | 数据来源、接口、允许的 AI 服务、账号或环境由谁提供 |
| 交付物 | 源码、说明、部署配置、演示或正式运行环境分别包含什么 |
| 验收标准 | 客户可操作的场景、输入与预期结果、适用性能和质量要求 |
| 时间与费用 | 交期、费用说明、第三方持续费用、修改与维护范围 |

数据与表格、文档、图文、短视频作为独立服务线后续开放。本期开发项目可以交付测试报告、操作文档等必要材料，这不等于已经上线“文档处理”服务。数据模型保留服务类型扩展，但不提前实现其余四套完整表单、检查和运营流程。

## 3 强制审核与技术整理

### 3.1 客户提交后的处理

提交回执显示“待审核”，需求仅对所属客户及有权限的内部人员可见。客户可查看进展并回答澄清；大厅列表、搜索、推荐、数量统计及大厅详情入口均不能泄漏未审核需求。客户自己的需求页和审核工作台不受大厅可见规则的混淆影响。

后台审核包含两部分，两者均完成后才能通过：

- **合规性审核：** 按已定义的受理政策检查用途、任务内容、资料权限及明显不适合承接的要求；证据不足则补充或拒绝。具体准则由业务负责人结合实际经营要求建立，不能仅凭 AI 评分判定。
- **技术整理：** 内部人员把客户描述整理为可执行范围、依赖、成果、验收、时间和费用约束，识别需要客户补充或确认的内容。

AI 可以辅助提取问题和起草技术说明；最终通过、退回补充或拒绝由有权限的内部人员操作并记录理由。创建账号、提交成功或得到 AI 回复都不能视为审核通过。

### 3.2 发布依据与版本

保留客户原始描述、澄清记录、整理稿、审核结论和发布版本，不直接覆盖客户原话。建议整理稿发给客户确认后再发布；如果先发布待完善的摘要，也必须明确未确认项，执行前双方确认最终范围。**客户确认是否作为发布前置条件尚待冻结；后台审核通过是用户已明确、不可绕过的发布前置条件。**

只有当前发布版本的合规及技术审核均有效、需求处于可发布状态，发布动作才成功。列表读取和详情访问也要校验有效版本，不能只靠管理端隐藏按钮。被拒绝、撤回、下架或审核失效的内容不能继续在大厅显示为可接任务。

重要字段修改后，新版本重新审核。建议审核期间大厅下架该任务，避免继续按旧范围接单；已成立的合作保留原确认版本，按变更流程处理。审核结果不能自动沿用到改写后的需求。

### 3.3 私有材料与大厅摘要

大厅展示经审核的必要任务摘要。源码、业务数据、凭证、联系方式及客户私有附件按任务和角色授权，不随发布动作变成公开资源。建议当前大厅仅向已登录且有有效内部承接授权的账号开放；是否允许游客或普通客户浏览公开摘要为待定产品规则。

2026-10-13 补充的用户明确需求：大厅与任务详情允许展示随审核发布版本公开的截图、视频和参考附件，各类资料均为可选；只有文字的任务不保留空媒体区。截图可查看放大，视频可播放；DOC/DOCX、TXT、MD、XLS/XLSX、CSV、PPT/PPTX、PDF 均需支持预览，所有当前有权访问的附件可下载原文件。设计需区分图片浏览、视频控制、文档/PDF 翻页、表格工作表与横向滚动、幻灯片切页，覆盖加载、预览准备、失败重试与下载进度。附件名、封面及数量同样受资料访问权限约束。本轮先经 MCP 修改 MasterGo 效果图，用户确认后再同步 APPClient；格式转换、预览及下载的真实服务仍待技术选型和实施。

## 4 账号准入与接单方式

### 当前内部账号

内部账号由有权限人员创建或邀请，成员本人激活并使用独立账号登录；不采用多人共享凭证。至少记录账号状态、角色、内部接单授权及操作历史。普通客户不能通过自助切换角色获得承接权限。

内部接单授权与正式认证分别表示。当前没有完成未来考核，不显示“OPC 已认证”徽章；内部可接单的依据是有效内部授权。账号停用或授权撤销后，不能继续查看受限大厅、接新任务或提交成果；在途合作进入运营接管流程，原交付记录保留。

### 大厅承接规则

2026-10-26 用户已明确：**授权成员检索已发布未承接需求 → 与需求客户独立沟通并提出绑定发布版本的条款 → 客户先在手机确认范围和条款 → 该承接者一键承接 → 项目立即归属本人并进入执行中**。当前仅面向内部授权账号，不能扩展为开放竞标；客户同意不能由承接者代为填写。范围或提案更新后重新确认。实现见[自主承接流程](../development/provider-claim-workflow.md)。

无论采用哪种方式，都需要校验账号授权、任务发布与审核版本、任务可接状态和有效负责人，防止重复点击或并发接单产生两个有效主要合作。需求审核负责人可以与最终执行人员不同，内部技术整理也不等于已经承接制作。

改派或交接是运营处理异常的能力，不是已确认的所有任务默认入口。换人记录原因、材料与责任交接；旧成员的继续提交权限撤销，价格、范围和交期不能被静默改变。已经下载的文件不能声称已被远程收回。

### 未来认证准入

后续按“申请 → 考核 → 结果评定 → 获认证资格 → 在资格范围内接单”设计。考核内容、能力类别、有效期、复核、暂停、撤销与申诉另做产品规则。扩大开放前明确现有内部成员如何转入认证机制，避免永久绕过认证。

本期仅将账号来源、内部授权与认证状态分开建模，必要时展示“未认证／尚未开放认证”。不默认建设考试平台、公开入驻门户或未经确定的评分算法。

## 5 两个产品端与统一后端

| 产品端 | 技术与目录 | 已明确的业务职责 |
| --- | --- | --- |
| 手机端 | Flutter + Dart，APPClient，Android 与 iOS | 客户和承接者在同一 APP 中按权限使用：任务查看、注册登录、提交需求、查看审核与补充、接单、范围确认、沟通、交付、修改与验收 |
| 后台管理端 | Vue.js + TDesign Vue Next，FrontendAdmin | 合规审核、技术整理、澄清处理、发布下架、账号与接单授权、内部质检、客服、配置与审计 |

两端接入 BackendService 的统一业务服务，共用需求、审核、发布、接单、交付及验收记录。后台审核和下架更新同一份服务端状态，手机端按权限获取结果；手机提交的材料和反馈也进入同一套管理流程。本地数据库已采用 PostgreSQL 18.4 并完成初始化，本轮后端已采用 FastAPI 实施；两端使用独立持久 opc_integration 联调；既有 opc_dev 应用凭据及正式部署尚未完成。

三个源码项目目录固定对应：**APPClient/ 为手机端，FrontendAdmin/ 为管理端，BackendService/ 为共用后端**。DB、Docs、Mockup 分别保存数据库脚本、文档与原型资料，不增加第三个前端产品。

下面是角色分工，客户与承接者是手机端内的角色，不是额外两个产品端。

| 角色或端 | 首版重点 |
| --- | --- |
| 日本客户 | 注册登录、提交需求、补充资料、查看审核状态、确认整理后的范围及费用、沟通、查看交付、修改与验收 |
| 内部承接者 | 指定账号登录、浏览获授权的大厅、按已定规则接单、查看本人合作、执行与交付 |
| 后台审核与技术人员 | 待审队列、合规结论、技术整理、澄清、发布及下架、版本记录 |
| 运营与管理员 | 账号与接单授权、接单确认或接管、客服、异常、配置、审计 |
| 内部质检人员 | 按已确认标准检查交付，记录问题，决定是否可对客提交 |

手机端必须完成正式业务操作，不能将交付或验收引导到另一个 OPC 桌面门户。承接者可在外部开发工具制作代码，在手机中通过系统文件选择上传约定源码包，或提交客户可取用的仓库链接与固定版本，并补充交付说明、测试材料和版本记录。具体交付方式按合作约定选择；客户在手机中查看说明、报告、可预览附件和演示入口，获取约定源码，提出修改或确认验收。

文件与源码入口需设计上传进度、失败重试、中断后恢复或重新选择、链接过期及版本提示，并用真实设备验证。手机业务闭环不要求在 APP 内编写、编译或执行任意客户代码；验收用例涉及外部系统或运行环境时，保留其实际验证证据，再在 APP 提交验收结果。

统一后端可以区分移动 API 与管理 API 的接口范围和响应字段，复用同一业务规则。手机客户或承接者的登录状态不能自动取得管理权限；管理操作需要独立授权和审计。统一后端不意味着两端共享管理员凭证或不加区别地返回全部业务资料。

小团队可兼任内部角色，但使用独立身份并记录实际操作人。公开服务者店铺、公开竞标和跨国匹配不进入当前默认开发包。

正式认证考核及另外四条服务线属于后续版本。P0 保留必要的数据边界，不以预留扩展为理由提前开发完整功能。

## 7 状态与交付规则

需求受理、审核、发布、承接和执行分别建模，避免一个“订单状态”同时承担全部含义：

| 对象 | 建议状态或关键事实 |
| --- | --- |
| 需求与整理稿 | 草稿、已提交、待补充、整理中、待客户确认、已确认、已撤回 |
| 审核版本 | 待审、审核中、通过、退回补充、拒绝；合规与技术两部分结果可追溯 |
| 发布 | 未发布、已发布、已下架；关联有效审核与发布版本 |
| 接单 | 可申请／领取、处理中、已确定负责人、已关闭；具体入口取决于选定机制 |
| 合作执行 | 待范围确认、待执行、执行中、内部检查、待客户验收、修改中、已完成、取消处理中 |
| 账号资格 | 账号启停、内部接单授权与未来认证资格相互独立，按实际策略共同决定可操作范围 |

软件交付至少包括约定的完整固定源码、运行或部署说明、环境变量样例、适用依赖与许可说明、实际测试结果和客户用例。可用约定仓库的固定提交且保证客户可取用并有约定归档，或提供完整源码包及校验值；演示链接不能替代源码交接。

未执行的测试不得记为通过；没有约定部署和持续维护，不能默认由内部承接者无限期承担。交付不包含生产密钥。平台本期不托管执行任意客户代码、SQL 或宏。

建议内部检查通过后对客户发布具体交付版本。内部备注和未发布稿与客户可见信息分开；内部质检不能代替客户验收。默认不设计超时自动验收。重要范围变化进入复审和重新确认；取消、成员停用、接管与验收冲突应有明确结果并保留审计。

## 8 日本本地化与资金

手机端默认日文，客户与内部承接者均可切换简体中文；后台管理端同样支持简体中文与日语。两端采用真实语言资源覆盖导航、表单、校验、状态、错误、空状态、按钮和弹窗，手机登录页及个人页提供切换入口。客户填写的需求、澄清、消息、交付说明与附件名属于原文，切换界面语言不自动翻译或覆盖这些内容，不改变需求、审核或发布版本，也不改变权限。整理稿及正式交付使用双方确认的语言，不能从 UI locale 推导交付语言。

APPClient 语言资源维护在 `lib/l10n/parts/*_{ja,zh}.json`，经合并脚本生成 ARB，再使用 Flutter `gen-l10n` 生成语言包。SharedPreferences 仅保存 `ja`/`zh` 语言偏好，重启恢复；退出账号、重置演示业务数据不清除选择，不因此存储凭证或业务资料。语言保存失败与界面即时切换分开处理，避免快速切换造成旧选择覆盖新选择。

建议默认 JPY 和 Asia/Tokyo 显示时区，金额、税费表达和期限在页面与接口中一致。UI 语言变化不改变时区、金额、已确认期限或资料区域。日本国内业务也要核对真实云、模型、邮件和日志的数据处理范围，不能自动认定不存在数据出境。

资金仍未定。当前内部履约不能直接套用旧开放撮合平台的“不代收付／托管分账”模型。应明确谁向客户签约和收费、是否线上支付、何时付款、退款及内部报酬是否由本系统处理。需求价格、合作完成与验收均不等于已收款；原型不默认加入钱包、抽佣或分账。

详见 [日本本地化](v1-japan-localization.md) 与 [三方准备](v1-third-party-services.md)。正式经营与客户条款按实际主体和收费方式核对，本方案不宣称相关手续已经完成。

当前大厅策略默认 `internal`。原管理录入策略 `assignment_mode=disabled/record_confirmed` 仍只控制后台记录既有关系；新的手机自主承接接口按客户实际确认、当前发布版本与内部授权独立校验。本地私有文件已有真实上传下载和人工检查证据，Office/PDF 已按 2026-10-25 说明接入本机转换；邮件推送、AI、支付及正式认证服务未接入。生产存储和异步投递供应商仍待确定。

## 10 MasterGo 到真实数据的工作流

按一条完整业务场景循环推进，而不是等全部页面画完才开始编码：

| 阶段 | 交付与通过条件 |
| --- | --- |
| 场景定义 | 明确角色、字段、状态和用例；强制审核、大厅可见与账号资格有一致规则 |
| MasterGo Vibe Design | 两套界面设计：手机客户与承接者角色、TDesign 管理端；包含交付验收及必要异常 |
| Vibe Coding 与 Mock | 在 Vue／Flutter 中实现页面、路由、表单和状态；固定样例可重置并贯穿完整流程 |
| 测试环境真实 API | 两端接入同一后端，验证审核发布、手机接单交付验收、角色隔离、状态版本、真实文件及通知 |
| 预发布与生产 | 实际设备和日本网络、正式配置、适用业务条件、恢复与回滚验证后发布 |

Mock 阶段同步定义接口契约，包含字段类型、可空、枚举、金额时间、分页、稳定错误码和版本冲突。界面经统一数据访问层选择 Mock 或真实 API，不在页面中写死模拟数据，真实失败不返回模拟成功。后端必须重新执行权限与业务规则。

用户先要求移除 APPClient Mock 角标，后于 2026-10-16 明确要求真实数据交付。本轮默认进入 API 配置，旧 Mock 仅保留显式测试／演示模式；未配置或接口失败不返回模拟成功。保持发布配置门禁：真实 release 要求 HTTPS，显式 Mock release 仍需演示开关。本地真实 PG 联调不等于支付、渠道签名或生产部署完成。

Vue 与 Flutter 分别按目标组件机制实现，复用业务语义与视觉规范；设计工具导出的参考代码需要适配和验证。浏览器移动布局不替代 Flutter 真机上的键盘、文件选择、返回及推送验证。MasterGo 当前连接与页面交付状态见 [APPClient 效果图](../../Mockup/app-v1-mastergo/README.md)，不能将适配器配置成功当成画布已完成。详见 [设计到生产流程](v1-design-to-production-workflow.md)。
