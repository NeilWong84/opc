# OPC V1 中国与日本国际化、本地化及上线条件

版本：规划草案 v0.1。编写及官方资料核查日期：2026-10-08（Asia/Shanghai）。

本文供需求拆解、原型、技术选型、供应商评估及发布计划使用，不代表已经实现功能、已选定供应商或已完成经营资质判断。与[项目背景](../project-context.md)、[竞品调研](../refs/competitor-research-2026-10-08.md)共同阅读；竞品功能与宣传不自动成为 OPC 需求。

## 1. 已明确方向、方案假设与适用范围

### 1.1 用户已经明确的方向

- OPC 面向中国和日本投放，平台定位仍是普通人的 AI 赋能副业接单、洽谈和合作交付。
- 中国和日本双方均可发布需求及承接服务，日本是重要需求来源，核心业务重心为日本需求与中国供给；同时支持中国需求由日本服务者承接及两国各自的国内供需业务。
- V1 包含五条并列核心服务线：Vibe Coding、AI 数据与表格、AI 文档、AIGC 图文、AIGC 短视频。Vibe Coding 占有重要比重，不能将软件、数据、表格、文档降为后续版本才支持。
- APP 使用 Flutter + Dart，后台前端使用 Vue.js + TDesign Vue Next；后端、数据库、云区域和 AI 供应商仍待选型。

### 1.2 本文采用的工作假设

- 建议 V1 以撮合、双语洽谈、合作确认、交付和验收记录为主，暂不由平台代收付。**这是待确认的建议，不是项目负责人已经决定的资金模式。** 无代收付也需要说明合同主体、报价币种、对账凭据及双方自行付款的边界，不得展示虚假的托管或到账保障。
- 首版在产品与流程上支持四种组合：中国需求方到中国服务者、中国需求方到日本服务者、日本需求方到中国服务者、日本需求方到日本服务者。各组合按实际主体、数据处理及业务条件启用，不整体延后中国需求方到日本服务者的反向跨境组合；其他市场另行扩展。
- 以可定义成果及验收标准的服务合作为产品基础；招聘雇佣、劳务派遣、无限期驻场运维等是不同的业务形态，需要另行定义。
- “普通人可借助 AI 接单”不等于任何用户都能承接生产系统、敏感数据库或高风险内容。按交付物、权限、影响范围和能力审核划分承接资格，不能仅靠工具名称判断。
- 本文的权限、最小样本、质检等条目属于建议的产品控制。法规条目另列触发条件与官方依据，不将所有产品建议写成法定义务。

## 2. 国际化不是只增加日文界面

建议从第一版数据模型中分开以下属性。字段名为概念示例，供后续技术设计采用或调整。

| 属性 | 含义与示例 | 必须避免的混淆 |
| --- | --- | --- |
| `ui_locale` | 界面语言与格式，如 `zh-Hans-CN`、`ja-JP` | 选择日文不等于日本用户、在日本居住或使用日本合同 |
| `communication_languages` | 双方可用于沟通的语言 | 会日文不等于可承诺专业日文质检 |
| `delivery_locale` | 成果所需语言、日期数字和排版规范 | 中文接单者可以交付日文软件、视频和表格 |
| `user_country_or_region` | 用户主动提供并按业务需要核验的所在地 | 手机区号和 IP 地址不是合同主体或常住地的充分证据 |
| `service_market` | 本次合作面向中国或日本市场 | 市场配置不随系统语言自动切换 |
| `contracting_entity_id` | 对该项服务承担合同责任的法律主体 | 品牌名、APP 发行账号、云账号不是同一概念 |
| `counterparty_type` | 个人、企业、个体经营者等业务身份 | 勾选“企业”不自动决定所有法律适用或税务结果 |
| `storage_region` | 数据实际保存区域 | 日本落盘不等于中国服务者读取资料没有跨境提供 |
| `processing_region` | 翻译、生成、转码、监控等实际处理区域 | 模型供应商总部、售卖站点和处理区域不能互相替代 |
| `contract_currency` | 双方确认的合同币种，如 CNY、JPY | 展示换算币种不能覆盖合同币种 |
| `agreed_timezone` | 交付和验收约定时区 | 服务器所在时区不能成为隐含业务规则 |

运营后台需要查看必要的地区、语言和合同信息，并按权限控制数据访问。不能只做“国内版/海外版”两个布尔开关来承载上述业务差异。

## 3. P0 国际化与本地化需求

### 3.1 界面、内容和通知

- APP 用户主流程同时提供简体中文和日文：注册登录、身份资料、服务与案例、需求发布、候选人/报价、聊天、合作确认、交付、验收、投诉、设置、账号删除。
- 文案使用稳定资源键，不将整句拆成多个片段拼接。错误、校验提示、空状态、加载失败、权限提示、邮件、推送和分享摘要均有本地化资源。
- 明确语言回退规则；缺少日文条目时不得静默展示未审核的机器翻译协议。对业务内容标示原文语言和译文状态。
- 语言切换保留编辑草稿与当前步骤，不修改合作币种、合同主体、地区权限和已接受协议。
- UI 日文经过母语或具备商务日文能力的人员检查；品牌、服务分类、状态名称建立中日术语表。客户可提供项目词汇表并在交付中冻结版本。
- 图中文字、录屏、示例附件和商店截图也需本地化。不能只有按钮变日文而案例和帮助仍全是中文。
- Flutter 原生本地化能力可作为实现起点，具体依赖与版本在技术选型阶段固定；本文不预先指定第三方国际化包。[Flutter 官方国际化说明，核查于 2026-10-08](https://docs.flutter.dev/ui/internationalization)

日本商务表达建议围绕明确的服务说明和条件：`見積`（报价）、`納期`（交期）、`修正回数`（修改次数）、`納品形式`（交付形式）、`検収`（验收）、`請求`（请款）。这是待日本需求方访谈验证的设计建议，不是对所有日本用户习惯的判断。

### 3.2 登录、姓名、企业资料和联系方式

- 不把中国手机号或微信设置为日本用户完成核心业务的强制条件。日本侧至少设计可行的邮箱登录/验证路径；其他登录方式按供应商接入结果确定。
- 手机号支持国际区号，展示与规范化存储分开；不套用中国 11 位手机号校验所有号码。
- 姓名支持汉字、假名、拉丁字符和空格，不强制所有人采用西式 first/last name。公司名、联系人名、昵称分开。
- 日本客户可以填写公司名称、部门、联系人及业务邮箱；假名读音仅在业务确需时提供字段，不以注册为由收集与服务无关的资料。
- 地址、邮编、税务与开票信息在相关业务动作中按需收集，不能因为“国际化”就强制所有用户填写完整地址和证件。
- 通知偏好、营销订阅与合作事件通知分别管理。日本方可通过站内消息和邮件完成协作，不依赖中国特定社交软件。

### 3.3 日期、时区和工作日

- 事件时间保存为 UTC；约定截止时间同时保存时区标识和用户确认的本地日期时间。地区时间采用 `Asia/Shanghai`、`Asia/Tokyo` 等 IANA 标识。
- 界面按用户偏好显示本地时间；正式合作页同时显示约定时区。例如“2026-10-15 18:00 JST（日本时间）/ 北京时间 17:00”。
- 禁止仅保存“明天”“三天后”“当地下班前”作为合作截止条件；相对描述必须转换成明确时间后让双方确认。
- 区分自然日和工作日；若承诺工作日，记录采用哪一方/哪一市场的日历及其版本。中国调休和日本节假日需要分别维护，不把星期一至五统一视作工作日。
- 日本国民祝日可参考内阁府公告，但客户公司休业、双方休假仍需单独约定。[日本内阁府国民祝日说明，核查于 2026-10-08](https://www8.cao.go.jp/chosei/shukujitsu/gaiyou.html)
- 提醒和逾期判断使用已确认的截止时刻；改变界面语言、旅行更换手机时区或重启服务不得改变截止时间。

### 3.4 CNY、JPY、报价和税费展示

- 每个合作确认版本固定一种合同币种。CNY 与 JPY 必须明确标出，不能仅用同为“¥”的符号区分。
- 金额使用精确类型；采用最小货币单位整数时，币种小数位规则不可写死为两位。JPY 报价和结果不得因格式化增加不存在的分单位。
- 可保留参考汇率展示，但需标明来源、时间和“参考”；不能依据新的参考汇率重新计算已确认的合同金额。
- 合同金额、参考折算金额、税额/税费说明、平台服务费及服务者预期到账金额分开。未接入支付时不显示平台实际结算金额。
- 日本侧明确税费是否包含、是否另有手续费；具体税务处理由交易主体、服务性质及客户身份确定，不能按语言直接套用统一税率。
- 发票、收据、报价单、合作记录是不同对象。平台生成合作确认记录不代表有资格代服务者开具当地税务票据。

### 3.5 双语聊天、需求和正式条款

- 消息与需求始终保留原文；译文记录来源语言、目标语言、译文版本、生成时间、引擎/模型版本及人工修订状态。
- 原文变更使旧译文标记为过期；不将旧译文继续展示成最新确认内容。原文、译文和修改历史可追溯。
- AI 翻译提示用于帮助理解。金额、日期、数量、否定条件、商用授权、维护责任等关键项用结构化字段交叉核对。
- 合作确认建立不可覆盖的版本快照，记录范围、交期、金额币种、修改次数、源文件、部署/维护责任、授权和验收条件。变更须形成新版本并记录双方确认。
- 中日条款出现歧义时进入澄清，不让系统自动选择对一方有利的译文。具有法律效力的基准语言及双语文本优先关系待主体与合同方案明确。
- 客户可要求原文保留、特定术语不翻译或人工复核。复制、导出、投诉证据均应能取得对应原文与版本。

## 4. V1 各核心服务的跨语言交付要求

以下五条服务线并列为核心服务。首版采用共用合作流程加不同的需求与验收模板，不把所有任务塞入图文视频模板，也不要求一次建成在线代码 IDE、数据库平台或完整 Office 编辑器。

| 服务 | 需求模板必须明确 | 首版交付与验收依据 | 中日协作重点 |
| --- | --- | --- | --- |
| Vibe Coding / 软件 | 业务场景、页面/功能清单、输入输出、目标设备浏览器、UI 语言、部署环境、已有代码权属、外部服务、权限边界、维护期限 | 可复现源码/版本、运行说明、依赖锁定或清单、环境示例、关键流程验证、约定的部署/演示、已知限制 | 日文 UI 与输入法、CNY/JPY/时区处理、日文帮助/错误、开源许可、客户资源与凭证隔离 |
| AI 数据与表格 | 字段说明、脱敏样本、清洗/转换规则、数据量级、输出结构、公式/统计口径、编码、日期和金额规则 | 转换规则说明、结果文件、行数与关键汇总核对、异常清单、可重复操作步骤或脚本 | 中日字符、全半角、前导零、JPY 整数、混合日期和时区、CSV 编码、跨境个人信息 |

### 4.1 Vibe Coding 的首版边界和验收

- 能力匹配要覆盖技术能力、案例、交付语言和工作量；不能把“会使用 AI 编程工具”视为已通过所有软件交付能力审核。
- 需求发布支持对已有系统的修复、功能增加及小型新应用，但必须写明影响范围。涉及生产权限、支付系统、关键数据修改等任务，应设置专门审核条件，而不是默认以普通素材任务开放。
- 平台保存合作范围、代码托管链接及约定交付版本；私有代码应使用用户授权的私有仓库或受控交付位置。公开案例只用客户授权的截图和经过清理的示例。
- 明确源码、配置模板、构建步骤、依赖清单、第三方服务费用、测试环境、部署说明、回滚/恢复说明及后续维护由谁承担。演示可访问不等于源码可复现；“AI 已生成”不等于验收完成。
- 建立开源和第三方资产清单，记录许可证、必要归属说明、修改情况及交付限制；依赖许可条件按实际使用方式核对。不能承诺所有生成代码零许可风险，不能将客户专有代码授权扩展为模型训练授权。
- 交付日文 UI 的软件至少验证日文输入法组合输入、假名/汉字、全半角、长文本、搜索、日期/金额和错误提示；接口标识符不应为翻译目的随意改名。
- 平台附件、聊天、需求和 AI 提示中禁止上传真实生产密码、私钥、数据库连接凭证、访问令牌和完整生产环境配置。以 `.env.example`、合成数据和最小测试权限完成开发；确需访问客户环境的，采用另行约定的最小权限、时限和撤销方式。
- 凭证扫描是辅助防线，不能保证完全识别。疑似泄漏应阻止继续传播、通知相关方并要求轮换；从聊天界面删除不能被描述为已清除所有副本。
- 首版不在 OPC 服务端直接执行用户上传的未知代码、SQL、宏或脚本；需要在线执行时另行设计隔离环境、网络权限、资源限制与安全验证。这不影响首版承接和记录相关服务。

### 4.2 数据、表格和文档不能按普通附件处理

- 需求阶段优先提交字段结构、业务规则及足以描述问题的合成/脱敏样本，不默认要求上传全量数据库、客户名单或员工记录。
- 处理完整业务数据前，明确其中个人信息、敏感信息、商业秘密、接收者及允许的模型工具。未能满足约定处理条件时，可改为客户环境处理、只交付脚本或只处理最小样本。
- 脱敏不等于必然无法再识别；去掉姓名但保留精确地址、联系方式或可关联 ID 的样本，仍需按实际风险分类。
- 表格验收包含：输入输出行数、去重规则、空值、异常值、前导零、长编号、精度、公式与结果、筛选/隐藏行，以及是否包含宏/外部链接。
- CSV 明确编码、分隔符、引号、换行与目标软件版本；UTF-8 可作为建议默认，客户既有 CP932/Shift_JIS 流程按约定输出并检查不可表示字符，禁止静默替换乱码。
- 金额列注明币种；不把 CNY 与 JPY 未经确认相加，不把税前/税后混为一列。日期声明格式与时区；不能将 `01/02` 擅自解释成唯一日期，也不能把日期型数据静默变为文本或序列号。
- 文档以客户模板和读者为准，验收中日字体、标点、段落、禁则、分页、目录、表格、页眉页脚、引用、链接及导出稿；横排、竖排和假名注音按实际需求约定，不因日本市场默认全部启用。
- AI 摘要、翻译、统计和重写须由服务者检查事实、数字与遗漏；结果文件与所用规则版本关联，便于客户指出可复现的问题。

### 4.3 AIGC 内容权利与日文质检

- 素材来源记录为自有、获授权、第三方许可或仅作参考；分别标明是否可生成加工、是否可向指定第三方工具提供、是否可公开展示。
- 图库、字体、音乐、配音、人物肖像/声音和品牌素材的使用范围分别记录。持有文件不自动说明已取得生成、训练、克隆或广告用途许可。
- 以实际工具条款与素材许可确定使用范围；不能承诺全部 AI 生成物天然具有完整、排他的可转让著作权。文化厅相关资料可作为权利检查参考，不是每件作品权利状态的认证。[日本文化厅 AI 与著作权资料，含 2024-07-31 清单](https://www.bunka.go.jp/seisaku/chosakuken/aiandcopyright.html)
- 人物声音克隆、真实人物替换及容易形成仿冒的内容建议首版不作为默认开放服务；如确需承接，应有独立的身份/授权核验与使用边界。
- 日本成品检查涵盖人名品牌读音、日文自然度、字幕错字、敬语/语气、数字价格、产品事实、文字溢出和投放规格。AI 评分可辅助，不能替代明确人工责任。
- 每类服务均由服务者自检；日本订单按类别、风险和合作承诺安排人工日文检查。高风险承诺和正式条款逐项检查，低风险内容可采用抽检，但需让客户知道适用的服务等级。
- 客户验收不自动授权平台公开案例；公开案例、宣传和模型训练另行管理授权。

## 5. 主业务跨境数据流与落地条件

### 5.1 日本存储不能替代跨境设计

主路径为日本需求方将资料交给中国服务者。文件即使保存在日本，中国接单者、中国客服或境外模型读取资料，仍需对提供与处理关系逐一评估。日本 APPI 对外国第三方提供有专门规则，判断也涉及法人关系、接收者角色和具体处理方式；不能只用存储机房国家给出结论。[PPC 外国第三方提供指南，页示 2025-12 修订](https://www.ppc.go.jp/personalinfo/legal/guidelines_offshore/)

中国侧，境内个人信息向境外提供的适用条件与豁免需结合数据类型、数量和业务目的判断；满足部分出境手续豁免，不等于免除告知、保护、影响评估等所有义务。[网信办《促进和规范数据跨境流动规定》，2024-03-22](https://www.cac.gov.cn/2024-03/22/c_1712776611775634.htm)

### 5.2 需要在技术选型前画出的数据流

| 数据流 | 典型内容 | 必须记录和核对 | 建议工程落实 |
| --- | --- | --- | --- |
| 日本需求方 → 中国服务者 | 需求、联系人、素材、代码、表格、文档 | 接收者身份/国家、处理目的、授权及允许再委托、保存和删除 | 文件分级、合作级访问控制、可追溯授权、有效期 |
| 日本需求方 → 日本服务者 | 同上 | 数据是否再转给中国运营、境外 AI、监控或备份 | 不能仅按双方在日本推定全程境内处理 |
| 中国需求方 → 日本服务者 | 需求、联系人、素材、代码、表格、文档 | 中国个人信息出境条件、资料权属、接收者角色、允许工具及再委托 | 与正向跨境共用授权和策略机制；按实际条件启用，不整体排除该合作组合 |
| 中国需求方 → 中国服务者 | 同上 | 数据是否仍发往境外 AI、监控、备份或其他处理方 | 国内双方合作也不自动代表无跨境数据流 |
| 中国用户 → 日本需求方 | 资料、聊天、作品、交付及合作记录 | 个人信息出境情形、最少必要字段、保留期限 | 联系方式按合作阶段披露，公开资料与订单资料分离 |
| 双方业务资料 → 翻译/生成工具 | 对话、提示、文档片段、代码、参考图、音频 | 实际处理区域、工具许可、是否训练、留存、子处理者 | 服务器 AI 网关、按订单与文件策略路由、最小输入 |
| 业务系统 → IM/邮件/推送 | 消息正文、附件链接、设备令牌、通知 | 供应商区域、跨境路径、日志留存和可见者 | 邮件/推送避免包含敏感正文；附件用受控链接 |
| 业务系统 → 日志/监控/客服 | 错误、请求、账号标识、工单 | 是否包含文件内容、生产凭证和个人信息 | 日志脱敏、采样、权限、按区域配置和期限删除 |
| 用户上传 → 备份/审核/转码 | 文件、媒体元数据、检测结果 | 复制位置、处理方、删除传播与期限 | 私有存储、生命周期、访问审计、转码标识保留 |

每条流至少形成一条处理活动记录：数据类别、来源、接收者、目的、范围、处理/存储区域、保存期、再委托、用户信息提供、处理依据及删除方式。初期可用运营清单维护，不必先开发复杂治理平台。

### 5.3 首版文件和 AI 网关控制

1. 文件上传时区分公开案例、合作资料、证件/身份资料及敏感业务资料；不将所有附件放在同一个公开桶。
2. 私有对象存储、短时授权链接、最小权限、下载审计与生命周期删除。明确这些控制不能阻止所有截屏、离线复制或已下载副本。
3. 译文和生成调用通过服务器统一接口；密钥不下发客户端；检查用户/合作权限、文件策略、允许工具和处理区域后调用。
4. 同一份文件混合普通内容和敏感信息时，先切分、最小化或脱敏；无法确定的资料不自动整份发送模型。不能因功能叫“翻译”或“摘要”而跳过检查。
5. 用户可以声明工具与处理区域限制；服务者承接前确认可满足。未满足时转为人工/客户环境处理或重新协商，而不是接单后静默改变工具。
6. 模型返回、上传和公开传播内容分别检查；保存必要的来源、调用版本及 AI 标识状态，日志避免长期保留完整敏感提示。
7. 账号删除、合作资料保留、争议证据保全与供应商删除分别设计；依法或依约保留的项目应向用户说明范围与期限，不能承诺一键立即擦除一切历史。
8. 公司主体变化、新增供应商、调整区域、扩大数据类别或服务范围时，重新检查对应数据流，不把首次接入结论视作永久有效。

| I18N-08 | 需求/消息翻译更新 | 原文可见，修改后旧译文失效；可追溯翻译版本、人工修改；关键金额/否定词检查样例通过 |
| I18N-09 | 合作条款版本 | 双方确认同一版本；变更需要新确认；导出和工单证据能还原原文、译文及确认时间 |
| I18N-10 | 日文 Vibe Coding 项目 | 用日文需求完成范围确认、源码/构建/说明交付及验收；日文 UI、时区金额和输入法测试有记录 |
| I18N-11 | 软件权限与许可 | 提交物不含生产凭证；依赖/许可清单和配置示例齐全；客户能按约定复现关键流程；额外费用与维护边界明确 |
| I18N-12 | 中日数据/表格任务 | 样本最小化，行数和汇总可核对；前导零、长编号、JPY、混合日期、UTF-8 与约定编码文件无静默损坏 |
| I18N-13 | 中日文档任务 | 日文自然度、数字、引用、字体和分页经检查；可编辑稿与预览稿一致，客户模板未被无意破坏 |
| I18N-14 | 日文 AIGC 图文成品 | 图中文字、字体、品牌名、产品事实、金额和渠道规格通过约定质检；素材许可与 AI 标识记录存在 |
| I18N-15 | 日本资料由中国服务者读取 | 对应处理记录、权限与披露/依据可查；无权限账号无法访问；不能仅用日本存储位置作为通过证据 |
| I18N-16 | 有区域/工具限制的附件 | 不允许的模型/翻译路由被阻断；可以转人工或重新协商；审计能说明实际调用何供应商/区域 |
| I18N-17 | 敏感混合文件与凭证 | 不自动向 LLM 发送完整资料；疑似凭证有处置路径；无法判断时进入明确的人工处理状态 |
| I18N-18 | 上传、转码、下载和公开案例 | 私有资料授权有效期生效；公开案例有独立授权；约定 AI 标识与元数据在处理后按要求保留 |
| I18N-19 | 通知与地区网络 | 日本真实邮箱/设备与中国真实网络完成验证；消息可在站内补查；无强制微信或 GMS 前置条件 |

| I18N-23 | 中国需求方到日本服务者 | 需求发布、双语洽谈、合作确认、文件/代码等交付和验收流程可用；启用条件与数据策略可查，不能以反向合作为由整体拒绝 |

至少准备四种组合的端到端合作样例：中国需求方到中国服务者、中国需求方到日本服务者、日本需求方到中国服务者、日本需求方到日本服务者。样例合计覆盖五条核心服务线，各线均有独立需求模板与验收证据；可用合成/脱敏数据验证尚未具备真实数据启用条件的路径，但不能据此声称该真实业务已开放。日本需求到中国供给仍为重点验证路径，不能只用一个视频案例代表全部 V1 范围。

## 9. 上线准备、待决事项与可并行工作

### 9.1 影响选型的待决事项

| 决策 | 为什么需要在对应设计前明确 | 本文建议的继续方式 |
| --- | --- | --- |
| 中日运营及签约主体 | 影响开发者账户、云与 AI 开户、合同、隐私和票据 | 先形成主体与责任图；界面和模板可先以可配置主体设计 |
| 撮合/代理/平台承包 | 影响是否由平台承诺交付、投诉责任和再委托关系 | 以撮合建议推进原型，将不同责任边界作为显式待决项 |
| 是否代收付及收费模式 | 影响支付可用性、跨境资金、税务、商店分类和退款 | 未决定前不接入“余额/托管/自动结算”；保留报价和合作金额数据 |
| 首批可承接任务及能力门槛 | 五条服务线均属 V1，但生产系统/敏感资料等复杂任务需要边界 | 按交付风险和能力分级，细化各类首批模板，不将某一核心类别整体延后 |
| 允许的资料与 AI 工具 | 直接决定主跨境路径是否能履行客户约定 | 用合成/脱敏样本开展功能和供应商验证；完整客户数据按处理条件开放 |
| 合同基准语言及争议流程 | 影响双语条款、确认快照和客服处理 | 原文/译文版本先建模，正式文本在主体方案确定后完成 |
| 日文质检与客服人员 | 决定可承诺的质量与响应时间 | 建立术语表、样例和工单流程，分配具备日文能力的责任人 |
| 地区部署与恢复方案 | 影响跨境访问、供应商合同、可用性与运维成本 | 先做数据流与性能验证，再决定单区/双区，不把双区当默认法律解法 |

### 9.2 可立即并行的产物

1. 五条核心服务线的中日需求表单、报价和验收模板；同一项目的中日对照样例。
2. 字段字典与地区/语言/币种/主体分离的数据概念模型。
3. 双语术语表、关键页面线框、通知与客服文案。
4. 数据流清单、允许工具清单和供应商验证题目；只使用合成或已获相应授权的样本。
5. 日本客户、在日服务者和中国服务者的试用访谈，验证理解与协作成本。
6. 按上表整理的发布材料与责任人清单，区分已完成、待外部接入、待业务决定。

### 9.3 首发前需要可审查的证据

- 四种合作组合在产品与流程上可完成，实际启用按主体、数据与业务条件逐项验证；五条核心服务线各有样例、明确交付边界及质量检查记录。
- 日本业务可以不依赖中国手机号/微信完成主要操作；国内业务可以不依赖 GMS 完成主要操作。
- 中日用户资料、文件、模型、IM、日志和客服访问的数据流已记录，适用手续、合同和处理条件有明确结论。
- 已启用的主体、条款、备案/登记、公示、商店资料和第三方数据声明相互一致；未具备条件的能力通过市场配置关闭并诚实说明。
- 日文内容与客服具有实际负责人；支持投诉、纠错、删除和权限撤销。
- 软件源码与许可、表格数据质量、文档排版、媒体版权及日文质量的验收证据能够分别追溯。
