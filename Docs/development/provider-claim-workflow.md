# 承接者工作台与自主承接

更新：2026-10-26。用户明确选择“客户先确认范围和条款，承接者再一键承接”。当前仅限有有效内部授权的账号，不表示正式 OPC 认证或开放竞标。此决定替代旧资料中“接单机制待定”的对应阶段表述。

## 手机流程

承接者底栏为首页、任务大厅、项目、沟通记录、个人设置。首页从本人有权读取的真实记录汇总：沟通中为未建立合作的本人沟通；进行中包含条款待确认的既有合作、开发中及修改中；已交付包含内部检查、待验收及已完成，以项目实际状态区分。取消项目不计入进行中或已交付。统计卡可跳到对应列表，最近项目可进入详情；没有编造完成百分比。

任务大厅仅展示当前双审通过并已发布、尚无有效合作的需求，检索标题和摘要。需求详情展示完整已发布范围及有权读取的参考资料，不公开客户原文私有附件。点击“沟通项目”建立需求客户与当前承接者的独立沟通；不同承接者之间不可读取对方的对话和提案。历史“向运营咨询”仍为 `consultation`，不会自动变成客户同意记录。

承接者在合作沟通页填写合作条款，可填写约定报价 JPY 和期限。提案绑定具体发布 ID；客户在自己的沟通记录进入对应承接者对话，核对范围、条款、报价与期限，显式确认后，承接者才出现“承接项目”。承接时再次确认，服务端创建唯一合作、负责人历史和条款版本，记录客户此前实际确认的账号和时间，以及当前承接者的确认，立即进入 `executing`。项目从大厅移除并进入本人项目。

开发中及修改中的本人项目在项目／沟通列表卡片及详情提供“提交交付物”。从列表打开前先定向刷新该需求；状态失效则停留最新详情。提交固定源码包或固定仓库 SHA、归档证据、操作说明、实际测试材料和交付说明后进入 `internal_review`；客户须待内部检查并对客发布后才能验收。

## 服务端契约

| 方法与路径（`/api/v1` 下） | 作用 |
| --- | --- |
| POST `/mobile/requests/{id}/negotiation` | 内部承接者与客户建立／复用独立沟通 |
| GET `/mobile/threads/{id}/negotiation` | 当前发布范围、最新提案、确认状态及可承接状态；消息使用既有消息接口 |
| POST `/mobile/threads/{id}/proposal` | 本沟通承接者提出条款；请求绑定 `publication_id`，使用幂等键 |
| POST `/mobile/claim-proposals/{id}/confirm` | 需求客户确认最新有效提案，携带 `expected_version` |
| POST `/mobile/claim-proposals/{id}/claim` | 提案承接者本人承接，携带 `expected_version` 和幂等键；返回合作 ID 和执行状态 |

请求锁顺序为需求→提案／合作。有效发布视图、账号授权、当前最新提案和确认版本均由服务端复核。新版提案使旧确认不可用于承接；换版、下架和别人已承接均阻止继续操作。请求锁与既有唯一约束保证竞争时只有一个有效合作；同幂等键重复请求返回同一结果。真实接口失败不回退 Mock。

`assignment_mode=disabled/record_confirmed` 继续只控制原管理录入接口；新手机流程由上述已明确的客户确认与承接校验控制，不要求打开管理录入。生产部署、支付、正式认证和自动扫描不在本次范围。

## 数据与维护

新增迁移 `007_provider_claim.sql`，不改历史迁移。增加 `negotiation` 会话类型和 `claim_proposals` 条款提案表；新表具备 `id/updated_usr/updated_at`、中文注释、并发版本、不可变条款与确认保护，以及可信事务元数据／审计触发器。客户确认只记录客户实际动作，不能由承接者提交任意客户 ID。提案被确认后不可改写；修改须新增提案并重新确认。

手机 HTTP 适配器保留幂等键和原始期望版本；所有列表通过当前账号有权访问的快照汇总。界面支持中日双语及浅深主题，原始消息和条款不随界面语言翻译。
